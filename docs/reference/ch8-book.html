menu_book 8. Oltre il Bit — Il libro

Un viaggio attraverso 12 capitoli: dal problema dell'embedded fragile al futuro dei DSL su VM deterministiche.

1. Il firmware è un castello di sabbia

"L'hardware mente. Il software mente. Il firmware... il firmware mente a entrambi." — proverbio degli ingegneri embedded

1.1 Una storia vera

Erano le 3 del mattino. Il drone stava eseguendo una missione di mappatura agricola — volo autonomo su 40 ettari di vigneto, sensore multispettrale, GPS RTK, quota 50 metri. Settimo sorvolo. Dati perfetti fino a quel momento.

Il sensore di umidità del suolo restituì un valore anomalo. Il firmware, scritto in C su un STM32, chiamò malloc per allocare un buffer di elaborazione. La memoria era frammentata. malloc restituì NULL. Il codice non controllò.

Segfault.

Il drone cadde.

Niente sensore rotto. Niente vento. Nessun errore di pilotaggio. Solo un puntatore nullo in una libreria I²C scritta otto anni prima da qualcuno che non lavorava più in azienda.

Costo del vigneto danneggiato: 12.000 €. Costo del drone: 8.000 €. Costo ore di sviluppo per investigare il crash: due settimane uomo. Costo di un if (ptr == NULL) prima di dereferenziare: zero.

Il problema non era la libreria. Il problema era l'architettura che permetteva a quella libreria di far cadere un drone.

1.2 Come siamo arrivati qui

L'embedded è nato come "scrivere codice per fare cose con i bit". Non c'era un sistema operativo. Non c'era un gestore di memoria. C'era un microcontrollore, un compilatore C (se andava bene), e tanta pazienza.

Poi le cose sono cresciute. I microcontrollori sono diventati più potenti, i firmware più complessi, i team più grandi. Ma l'architettura di base è rimasta sostanzialmente invariata:

void main() {
    init_hardware();
    init_peripherals();
    init_timers();
    
    while(1) {
        if (flag_tick_1ms)     handle_tick();
        if (flag_uart_rx)      handle_uart();
        if (flag_button)       handle_button();
        // ... altri 20 flag ...
    }
}

Questo pattern — il superloop — è ancora oggi la spina dorsale di milioni di dispositivi embedded. Ha 50 anni. Funziona. Ma ha un problema fondamentale: tutto è condiviso, nulla è protetto.

1.2.1 Lo heap è globale

Ogni malloc (o equivalente) attinge dallo stesso pool di memoria. Non importa se la chiamata viene dal task critico di controllo motore o da una libreria di logging usata raramente. Competono per la stessa risorsa.

// Task critico: controllo motore (1kHz)
void motor_control_task() {
    float* filter_buf = malloc(256 * sizeof(float));  // potrebbe fallire!
    if (!filter_buf) { /* e ora? */ }
    // ...
}

// Task di logging: ogni 60 secondi
void log_task() {
    char* msg = malloc(1024);  // frammenta lo heap
    sprintf(msg, ";Temperatura: %f", read_temp());
    log_send(msg);
    free(msg);
}

La frammentazione causata dal task di logging può far fallire il successivo malloc del task di controllo motore. Un task non critico può far crashare un task critico. Questo non è un sistema affidabile. È un castello di sabbia.

1.2.2 Lo stack è unico

Il superloop condivide lo stesso stack C per tutto: interrupt, chiamate di funzione, callback. Una ricorsione accidentale, un annidamento di interrupt troppo profondo, e lo stack collassa.

void uart_isr() {
    char byte = UART_DR;          // consuma stack
    process_byte(byte);           // consuma ancora stack
}

void process_byte(char b) {
    if (b == ESCAPE) {
        uart_isr();               // RIENTRO! Stack sotto stress
    }
}

Su un microcontrollore, uno stack overflow è indistinguibile da un reset. Non c'è una guardia. Non c'è un "stack overflow exception". C'è solo una sovrascrittura silenziosa di memoria, che si manifesta giorni o settimane dopo come un crash in un punto del codice completamente diverso.

1.2.3 Le interrupt sono prioritarie

Un'interrupt ad alta priorità può interrompere qualsiasi cosa — inclusa un'altra interrupt. Il prodotto di N annidamenti di interrupt e M priorità è un grafo di esecuzione così complesso che nessun essere umano può ragionare su di esso.

void TIM1_ISR() {        // priorità 0 (più alta)
    sensitive_operation();
}

void TIM2_ISR() {        // priorità 2
    shared_resource_modify();
}

void main_loop() {
    shared_resource_read();
    // TIM2_ISR arriva: modifica shared_resource
    // Poi TIM1_ISR arriva: sensitive_operation() vede shared_resource modificato!
}

Il risultato: race condition imprevedibili. Il sistema funziona per ore, giorni, settimane. Poi, in una combinazione specifica di tempistiche, si rompe. E non hai modo di riprodurlo.

1.3.2 Costi indiretti

  • Paura di toccare il codice — "funziona, non ci mettere le mani"
  • Dipendenza dal "guru" — la persona che ha scritto il codice 5 anni fa e sa perché certi delay sono "magici"
  • Impossibilità di test esaustivi — un sistema non deterministico non è testabile in modo deterministico

"La parte più costosa di un progetto embedded non sono i componenti. È l'incertezza."

1.4 Un paragone: come fanno i grandi sistemi?

I sistemi operativi moderni (Linux, Windows, macOS) risolvono questi problemi da decenni:

  • Processi isolati: un processo non può scrivere nella memoria di un altro
  • Memoria virtuale: la MMU traduce indirizzi, rileva accessi illegali
  • Scheduler preemptivo: nessun task può monopolizzare la CPU
  • Eccezioni di sistema: segmentation fault non fa cadere l'intero sistema

Perché i microcontrollori non fanno lo stesso?

Perché non hanno una MMU. Non hanno hardware di protezione della memoria. Non hanno un sistema operativo che isoli i processi. Un microcontrollore tipico ha 256 KB di flash e 64 KB di RAM — troppo poco per Linux, troppo poco per una MMU software.

Ma la domanda giusta non è "perché non possiamo mettere Linux su un MCU?". La domanda giusta è: "cosa possiamo costruire che dia lo stesso isolamento con una frazione delle risorse?"

Caldeira VM è la risposta.

1.5 L'illusione della "programmazione difensiva"

La cultura embedded tradizionale insegna la programmazione difensiva: controlla ogni puntatore, inizializza ogni variabile, verifica ogni allocazione.

void safe_operation() {
    char* buf = malloc(256);
    if (!buf) {
        log_error(";OOM in safe_operation");
        return ERROR_OOM;
    }
    // ... 50 righe di codice ...
    if (some_condition) {
        free(buf);
        return OK;
    }
    // ... altro codice ...
    free(buf);
    return OK;
}

Questa funzione ha 5 percorsi di esecuzione. In 4 di questi, free(buf) viene chiamato. In 1, viene chiamato log_error e si esce senza free. Se domani qualcuno aggiunge un sesto percorso e dimentica free(buf), hai una memory leak. Il sistema funziona per 3 giorni, poi OOM.

La programmazione difensiva non risolve il problema strutturale: lo nasconde. Sposta la responsabilità dalla piattaforma allo sviluppatore. E su un progetto con 200.000 righe di C, la probabilità che un percorso di errore dimentichi un free si avvicina a 1.

1.6 E gli RTOS?

"Basta mettere un RTOS" è la risposta più comune. FreeRTOS, Zephyr, NuttX, Azure RTOS. Risolvono il problema dello scheduling, ma non quello dell'isolamento.

void critical_task(void* params) {
    while(1) {
        int* p = (int*)0x20001000;  // indirizzo di un altro task
        *p = 42;                     // corruzione silenziosa
        vTaskDelay(10);
    }
}

Un RTOS tradizionale non impedisce a un task di scrivere sulla memoria di un altro task. Non c'è protezione. Non c'è isolamento. C'è solo un falso senso di sicurezza dato dal "multitasking".

Inoltre, un RTOS aggiunge complessità:

  • Priorità: la scelta della priorità giusta è un problema NP-hard nella pratica
  • Priority inversion: un task a bassa priorità blocca uno ad alta
  • Deadlock: due task che si aspettano reciprocamente
  • Stack di ogni task: devi stimare lo stack di ogni task — se sbagli, stack overflow

FreeRTOS+Trace, il tool di analisi di FreeRTOS, costa 2.500 €/anno. Non perché sia caro. Perché senza di esso, non hai idea di cosa stia succedendo nel tuo sistema.

1.7 Il costo nascosto del "nudo e crudo"

C'è una credenza radicata nell'embedded: "su microcontrollore si scrive in C (o peggio), perché un OS o una VM consumano troppe risorse".

Analizziamo il costo reale, non quello percepito.

Costi evidenti (quelli che tutti vedono)

Il costo upfront: 4 KB di RAM, 16 KB di flash, 15% di CPU. Su un ESP32-S3 con 512 KB di RAM e 16 MB di flash, questo costo è trascurabile.

Il costo nascosto annuale del C nudo su un progetto embedded tipico è facilmente 100.000 € tra debug, porting e certificazione.

La domanda non è "posso permettermi una VM?". La domanda è: "posso permettermi di NON averla?".

1.8 La grande menzogna: "funziona"

Ogni progetto embedded ha una fase in cui il firmware "funziona". Il semaforo scatta, il LED lampeggia, i dati arrivano. Il PM è contento. Il cliente firma.

Poi il prodotto va in produzione. E:

  • Il primo lotto di 1.000 dispositivi funziona perfettamente
  • Il secondo lotto di 10.000 inizia a dare problemi "ogni tanto"
  • Il terzo lotto è un incubo: il 5% dei dispositivi crasha entro 24 ore

Non è un problema di produzione. È un problema di non-determinismo. Il tuo firmware funziona nel tuo laboratorio perché la temperatura è 25°C, il pin di trigger non oscilla, l'alimentatore è stabile. In produzione, la temperatura varia, i segnali oscillano, l'alimentatore rumoreggia. E i percorsi di codice che non avevi mai testato iniziano ad eseguire.

Un sistema non determinista non è testabile. E un sistema non testabile è una scommessa.

1.9 Schema narrativo: la checklist

Ecco una checklist onesta. Quante di queste condizioni descrivono il tuo progetto?

  • [ ] Usi malloc o equivalenti a runtime
  • [ ] Hai una funzione con più di 3 percorsi di errore
  • [ ] Le interrupt condividono dati col main loop senza mutex
  • [ ] Stimasti lo stack "a occhio" e non hai mai verificato
  • [ ] Hai un watchdog timer che resetta il sistema "per sicurezza"
  • [ ] C'è una variabile globale modificata in più punti
  • [ ] Non sai esattamente quanto impiega ogni percorso di codice
  • [ ] Hai avuto almeno un bug in produzione che non sei riuscito a riprodurre in laboratorio
  • [ ] Hai detto "tanto funziona" almeno una volta nell'ultimo mese

Se hai spuntato anche solo una di queste, il tuo castello di sabbia è destinato a crollare. Presto o tardi.

1.10 La svolta: e se il problema fosse l'architettura?

Per decenni abbiamo cercato di risolvere i problemi dell'embedded aggiungendo cose: più astrazioni, più librerie, più tool, più processi. RTOS, HAL, framework, generatori di codice. Ogni strato prometteva di essere la soluzione.

Non lo è stata. Perché il problema non è la quantità di strati. È che non c'è un confine netto tra ciò che è affidabile e ciò che non lo è. Tra ciò che è isolato e ciò che è condiviso. Tra ciò che è determinista e ciò che è best-effort.

Un'architettura che non garantisce isolamento non è affidabile. È solo fortunata.

Caldeira VM parte da un presupposto opposto: invece di cercare di proteggerti da te stesso (programmazione difensiva, code review, lint), progetta la VM in modo che certi errori siano strutturalmente impossibili.

  • Non puoi scrivere fuori dalla tua regione di memoria — la VM controlla ogni accesso
  • Non puoi frammentare la memoria — non c'è free list
  • Non puoi bloccare la CPU all'infinito — lo slicer ti ferma
  • Non puoi corrompere lo stato di un altro evento — ogni evento parte pulito
  • Non puoi perdere un errore — GUARD lo cattura

Questo non è "programmazione difensiva". È architettura difensiva. La VM protegge il tuo codice da te stesso. Sempre. Non "di solito". Non "se ti ricordi di controllare il puntatore". Sempre.

2. Macchine virtuali su MCU

"Qualsiasi problema può essere risolto aggiungendo un livello di indirezione... tranne il problema di troppi livelli di indirezione." — adattato da David Wheeler

2.1 La prima reazione

Quando senti "macchina virtuale su un microcontrollore", la prima reazione è quasi sempre la stessa:

"Ma dai, è un ESP32. Ha 512 KB di RAM. Ci metto una VM e mi resta la metà. E poi la lentezza. Un'istruzione in C diventa 10 istruzioni VM. Un loop che doveva girare a 100 kHz gira a 10 kHz. Non si può fare."

È la stessa reazione che ebbero gli ingegneri IBM quando sentirono parlare di macchine virtuali per la prima volta. Era il 1967. Il System/360 aveva appena dimostrato che era possibile astrarre l'hardware via software. Eppure, passarono altri 30 anni prima che le VM diventassero mainstream — con la JVM, poi .NET, poi JavaScript V8, poi WebAssembly.

Oggi, nessuno si stupisce di una VM su un browser, su un server, su un telefono. Ma su un microcontrollore? "È follia."

E se non lo fosse?

2.2 Una breve storia delle macchine virtuali

1967 — IBM System/360 Model 67

La prima macchina virtuale commerciale. Permetteva di eseguire più sistemi operativi sullo stesso mainframe. Il costo? Raddoppiava il tempo di esecuzione. I dirigenti IBM erano scettici. I clienti no — preferivano pagare il doppio per due OS in uno piuttosto che comprare due mainframe.

Nascita del compromesso: prestazioni vs flessibilità.

1970 — Forth

Chuck Moore crea un linguaggio che è anche una VM. Le parole Forth vengono compilate in bytecode eseguito da un interprete minimalista. Un sistema Forth completo sta in 8 KB. Funziona su microprocessor con 1 KB di RAM. Viene usato per telescopi, robot, controlli industriali.

Prima dimostrazione: una VM può essere più piccola del codice che sostituisce.

1995 — Java Virtual Machine

Sun lancia Java con la promessa: "write once, run anywhere". La JVM è un'astrazione software che traduce bytecode in istruzioni native. Il costo iniziale è alto (10-20x di overhead). Ma il vantaggio è enorme: il codice Java funziona su qualunque architettura.

La VM come layer di portabilità.

2006 — LuaJIT e scripting embedded

Mike Pall crea LuaJIT, una VM Just-In-Time per Lua. Lua diventa il linguaggio di scripting embedded più diffuso — usato in router, console, videogiochi. La VM occupa 80 KB. L'overhead è del 10-30%. E Lua è un linguaggio sicuro: niente puntatori, niente buffer overflow.

La VM come layer di sicurezza.

2019 — WebAssembly (WASM)

WASM diventa standard W3C. Esegue codice sandboxed in un browser a velocità quasi-native. La specifica è progettata per essere compilata da C/C++/Rust, non per essere scritta a mano. L'isolamento è garantito dall'architettura della VM, non dal sistema operativo.

La VM come sandbox universale.

Oggi — Caldeira VM

Caldeira è l'evoluzione naturale di questa storia: una VM nata per l'embedded, senza compromessi su determinismo e isolamento. Non è un linguaggio general-purpose (come Java o Lua). 2.3 Cosa intendiamo per "macchina virtuale" in questo contesto

Una macchina virtuale è un livello software che traduce istruzioni da un formato intermedio (bytecode) a istruzioni native. Il bytecode non viene eseguito sul processore fisico, ma su un processore virtuale — la VM.

┌────────────────────────────────────────────┐
│              Codice Sorgente               │
├────────────────────────────────────────────┤
│                 Compilatore                │
├────────────────────────────────────────────┤
│               Bytecode (.lava)             │
├────────────────────────────────────────────┤
│           Macchina Virtuale (VM)           │
├────────────────────────────────────────────┤

In Caldeira, la VM è un interprete di bytecode. Legge un'istruzione alla volta, la decodifica, e la esegue. Niente JIT, niente recompilazione. Semplice, lineare, prevedibile.

Il costo? Una VM interpretata è naturalmente più lenta del C nudo, ma il costo è fisso e prevedibile. Non "di solito veloce e a volte lentissimo per un page fault". Sempre lo stesso. Sempre.

2.5 L'illusione della velocità

C'è un esperimento mentale che faccio spesso con gli ingegneri embedded:

"Quanto è veloce il tuo firmware?"

La risposta è quasi sempre una stima: "il loop di controllo gira a 10 kHz, il polling del sensore a 100 Hz, l'UART a 115200 baud".

"Quanto impiega ESATTAMENTE ogni percorso?"

Silenzio.

"E quanto tempo sprechi in attesa?"

"Beh, c'è un delay qui, un polling là..."

"Quanto?"

"Non lo so. Funziona."

Il mito della velocità nell'embedded è che dobbiamo ottimizzare ogni istruzione. La realtà è che passiamo la maggior parte del tempo ad aspettare.

Un ESP32 a 240 MHz ha tempo da vendere. Un delay_ms(1) buttato via è una quantità enorme di potenza di calcolo sprecata. Un polling di un flag UART a 115200 baud consuma CPU in attesa che un bit arrivi — e un bit a 115200 baud dura 8.68 μs, un'eternità per la CPU.

Il vero costo del firmware embedded non è la VM. È l'attesa implicita che non sai di avere.

Caldeira non elimina l'attesa. La rende esplicita. Invece di polling, usi eventi. Invece di delay, usi YIELD. Invece di "spero che arrivi in tempo", sai esattamente quante istruzioni esegui.

2.8 Portabilità: una VM ti segue per tutta la vita

Uno dei vantaggi meno discussi di una VM è la portabilità hardware.

Con C nudo, cambiare MCU significa:

  • Riscrivere i driver (GPIO, UART, I²C, SPI, timer)
  • Adattare il linker script e la mappa di memoria
  • Ricompilare con toolchain diversa
  • Testare tutto da capo (i nuovi driver hanno bug nuovi)
  • Scoprire che il nuovo MCU ha un errata che il vecchio non aveva

Tempo stimato: 4-8 settimane per un progetto medio.

Con Caldeira VM, cambiare MCU significa:

  • Portare le syscall (tipicamente 10-20 funzioni HAL)
  • Ricompilare la VM per la nuova architettura
  • Il bytecode è lo stesso — non devi toccarlo

Tempo stimato: 1 settimana per un progetto medio.

// Unico file da riscrivere: hal_arch.h per il nuovo target
static inline void hal_gpio_write(uint32_t pin, uint32_t val) {
    // Nuova implementazione per il nuovo MCU
    GPIO->;OUT = val ? (GPIO->OUT | (1 << pin)) : (GPIO->OUT & ~(1 << pin));
}

Il bytecode .lava è indipendente dalla piattaforma. Lo stesso file funziona su ESP32 e su Linux (in simulazione). Il core della VM è portabile per progettazione, ma al momento i target supportati sono PC ed ESP32. Scrivilo una volta, eseguilo dove la VM è disponibile.

2.9 Il caso Linux: la VM come simulatore

Uno dei vantaggi più pratici di Caldeira: la VM funziona identica su Linux e sul target embedded.

Durante lo sviluppo:

  • Compili il bytecode sul PC
  • Lo esegui con lava (la VM Linux)
  • Debughi con GDB
  • Testi con script automatici

Alla fine:

  • Carichi lo stesso .lava sul target
  • Funziona esattamente allo stesso modo

Nessuna differenza di compilatore. Nessuna differenza di libreria. Nessuna differenza di comportamento. Lo stesso bytecode. Lo stesso risultato.

Nell'embedded tradizionale, "funziona sul PC" e "funziona sul target" sono due frasi separate da settimane di debug. Con Caldeira, sono la stessa frase.

2.10 Sintesi: follia o necessità?

La risposta dipende da cosa stai costruendo.

  • Se stai costruendo un giocattolo — un LED che lampeggia, un sensore che logga — il C nudo va benissimo. Una VM è follia.
  • Se stai costruendo un prodotto che deve funzionare per anni, in ambienti difficili, con sensori, attuatori, comunicazione, logica complessa — una VM non è un lusso. È una necessità architetturale.
  • Se stai costruendo una piattaforma — un dispositivo che sarà programmato da altri, con linguaggi diversi, per domini diversi — una VM è l'unica scelta sensata.

Caldeira non compete con C per applicazioni semplici. Compete con l'incertezza, la fragilità, la non-determinabilità dei sistemi embedded tradizionali. E in questo, non è follia. È la scelta più razionale che puoi fare.

3. Determinismo come architettura

"Un sistema deterministico non è solo un sistema di cui conosci il risultato. È un sistema di cui conosci il risultato prima di eseguirlo."

3.1 Il mito del real-time

Nel mondo embedded, "real-time" è una delle parole più abusate. La usiamo per indicare qualsiasi sistema che deve rispondere entro un tempo prestabilito. Ma c'è un'abissale differenza tra:

Hard real-time: "Se il airbag non si apre entro 5ms dalla decelerazione, il passeggero muore."

Soft real-time: *"Se il display non si aggiorna entro 16ms, l'utente nota lo stuttering."**

Best effort: *"Di solito risponde in tempo. Per lo meno, non è ancora crashato."**

La maggior parte dei sistemi embedded si autodefinisce "real-time" quando in realtà è nella categoria "best effort". E il problema non è la velocità della CPU. Il problema è che l'architettura non garantisce nulla.

Un RTOS tradizionale ti dà:

  • Priorità ai thread
  • Semafori
  • Code di messaggi
  • Timer

Ma non ti dà certezze. Non ti dice:

  • Quanto tempo impiega esattamente malloc
  • Se un interrupt di priorità maggiore arriverà mentre il tuo thread critico sta eseguendo
  • Se un altro thread ha corrotto il tuo buffer
  • Se la catena di dipendenze del tuo task rientra nel deadline

Caldeira VM affronta il problema alla radice: non cerca di essere più veloce. Cerca di essere più prevedibile.

3.2 Il principio: ogni evento è un'isola

In Caldeira, l'unità di esecuzione è l'evento. Non il thread, non il task, non il processo. L'evento.

┌─────────────────────────────────────────────────┐
│                   Event Loop                     │
│                                                  │
│  ┌────────────┐  ┌──────────┐  ┌──────────┐   │
│  │EVT_TICK_1MS│  │UART_RX   │  │USER_CUST │   │
│  │ handler    │  │ handler  │  │ handler  │   │
│  └────────────┘  └──────────┘  └──────────┘   │
│       │              │              │          │
│       ▼              ▼              ▼           │
│  ┌─────────────────────────────────────────┐    │
│  │           Esecuzione VM                │    │
│  │  • PC = handler_addr                    │    │
│  │  • SP = stack_base                      │    │
│  │  • scratch = saved                      │    │
│  │  • slice = config.default_slice         │    │
│  │  • Esegui fino a HALT, YIELD o slice=0 │    │
│  └─────────────────────────────────────────┘    │
└─────────────────────────────────────────────────┘

Ogni evento:

  • Parte con SP resettato — non c'è stack residuo di eventi precedenti
  • Parte con scratch resettato — le allocazioni dell'evento precedente sono sparite
  • Ha un budget di istruzioni — lo slicer conta ogni istruzione eseguita
  • Non può corrompere altri eventi — la memoria è regionale, non condivisa

Non è "un thread che viene sospeso". È un esecuzione atomica che parte, fa il suo lavoro, e termina. Se non termina entro il budget, viene sospesa (YIELD) e ripresa al ciclo successivo.

3.3 Lo slicer: un contatore di istruzioni, non un timer

La maggior parte degli scheduler cooperativi usa timer hardware per il time-slicing. Un timer scatta, un flag si alza, lo scheduler cambia contesto.

Caldeira fa qualcosa di diverso: usa un contatore di istruzioni.

Ogni istruzione eseguita consuma una unità del budget. Quando il budget si esaurisce, la VM yielda automaticamente — non come errore, ma come comportamento normale.

Perché è meglio di un timer?

Aspetto Timer hardware Slicer Caldeira
Unità di misura Microsecondi Istruzioni
Predicibilità Dipende dal percorso di codice Esatta: N istruzioni = N decrementi
Overhead Interrupt, salvataggio contesto Un confronto e un decremento
Portabilità Dipende dal timer MCU Indipendente dall'hardware

Con lo slicer, sai esattamente che un evento esegue al massimo N istruzioni. Non "al massimo N microsecondi, a seconda se la cache ha fatto hit o miss".

Il default_slice di ogni evento è configurabile in events.def:

EVT_TICK_1MS ha 500 istruzioni di budget — sufficienti per la maggior parte degli handler rapidi. Eventi complessi (es. EVT_RESET) hanno budget piu' alto (5000). Se l'handler non finisce in tempo, yielda e riprende al ciclo successivo. Nessuna perdita di dati, nessun crash, nessuna corruzione.

3.4 MARK/FREE: memoria regionale

Un evento può allocare memoria nello scratch:

MARK          ; salva il punto di allocazione corrente
ALLOC R1, 64  ; alloca 64 byte, R1 = puntatore
...           ; usa R1
FREE          ; ripristina il punto di allocazione

Tutto ciò che viene allocato tra MARK e FREE viene rilasciato collettivamente. Nessuna free list, nessuna frammentazione, nessuna chiamata a free().

Perché è determinista? Perché:

  1. ALLOC è un incremento del bump pointer: O(1)
  2. FREE è un ripristino del bump pointer: O(1)
  3. Non c'è garbage collection
  4. Non c'è deallocazione individuale
  5. La frammentazione non esiste — è uno stack lineare

Puoi visualizzare lo scratch come un rullo di carta:

Prima di MARK:  [░░░░░░░░░░░░░░░░░░░░] allocatore
Dopo MARK:      [░░░░░░░░░░░░]↑       punto salvato
ALLOC 64:       [░░░░░░░░░░░░████████]↑  allocatore avanzato
FREE:           [░░░░░░░░░░░░]↑       allocatore ripristinato

Ogni evento ricomincia con un rullo nuovo. Le allocazioni di un evento non sopravvivono all'evento successivo.

Cosa succede se un evento non termina (YIELD)?

Se l'evento yielda, lo scratch non viene pulito — perché l'evento non è finito. Alla ripresa, l'evento trova lo scratch esattamente come l'ha lasciato, e continua ad allocare da dove aveva smesso.

Questo significa che uno yield in un'allocazione complessa (es. costruzione di una struttura dati annidata con più MARK) è perfettamente sicuro. L'unica regola: non yieldare dentro MARK (il core lo controlla e dà FAULT_ILLEGAL_YIELD).

3.5 Frame Arena: memoria che sopravvive

Non tutta la memoria deve essere temporanea. Per oggetti persistenti (buffer DMA, dati sensori, strutture di controllo), Caldeira ha una seconda arena: il Frame Arena.

┌─────────────────────────────────────────────┐
│              Frame Arena (condivisa)         │
│                                             │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐      │
│  │ OBJ  │ │ OBJ  │ │ FREE │ │ OBJ  │      │
│  │ A    │ │ B    │ │      │ │ C    │      │
│  └──────┘ └──────┘ └──────┘ └──────┘      │
│      ▲         ▲               ▲            │
│      │         │               │            │
│  Evento 1  Evento 2       Evento 3         │
└─────────────────────────────────────────────┘

Diversamente dallo scratch (privato per VM), il frame è condiviso tra tutte le VM e sopravvive agli eventi. Si alloca con:

NEW.FR R1, 0    ; nuova istanza classe 0 nel frame
ALLOC.FR R1, 64 ; alloca 64 byte nel frame

La gestione della memoria è a pagine (tipicamente 64 byte). MARK.FR e FREE.FR funzionano come per lo scratch, ma a granularità di pagina:

MARK.FR
ALLOC.FR R1, 128   ; consuma 2 pagine
NEW.FR R2, 1       ; consuma N pagine (in base alla size della classe)
FREE.FR            ; rilascia le pagine allocate dopo MARK.FR

Il frame condiviso tra più VM permette pattern di comunicazione inter-VM senza copia: una VM scrive, l'altra legge.

3.6 Pin/Unpin: proteggere la memoria dallo yield

Quando una syscall yielda, lascia lo scratch intatto. Ma se un altro evento esegue FREE.FR, potrebbe liberare pagine che la syscall stava usando.

Per questo esistono caldeira_pin_frame e caldeira_unpin_frame:

static void sys_async_read(VMContext* vm) {
    switch (caldeira_get_resume_id(vm)) {
    case 0:
        uint32_t buf = CALDEIRA_ARG_1(vm);
        caldeira_pin_frame(vm, buf, 1024);  // blocca 1024 byte
        hal_dma_start(buf, 1024);
        caldeira_yield(vm, 1);
        return;
    case 1:
        caldeira_unpin_frame(vm, CALDEIRA_ARG_1(vm), 1024);
        CALDEIRA_RETURN(vm, 0);
    }
}

Quando una pagina è pinnata (owner = 0xFF), FREE.FR la salta — la contrassegna come "differita" (0xFE). Quando arriva unpin_frame:

  • Se FREE.FR non è ancora passato → la pagina viene ripristinata al gruppo originale
  • Se FREE.FR è già passato → la pagina viene liberata immediatamente

Il risultato: le operazioni asincrone non perdono mai i loro buffer, indipendentemente da quanti FREE.FR avvengono mentre sono in attesa.

3.7 Recovery: GUARD per fault strutturali

Anche in un sistema deterministico, gli errori capitano. Un indirizzo non valido, una divisione per zero, un accesso fuori dai limiti.

Caldeira implementa un meccanismo di recovery strutturale basato su GUARD / UNGUARD:

GUARD fault_handler   ; salva il contesto corrente
    ALLOC R1, 1024    ; potrebbe fallire (OOM)
    LD32 R2, 0(R1)   ; potrebbe essere indirizzo non valido
UNGUARD               ; rimuove il guard

fault_handler:
    ; R14 contiene il codice fault
    ; SP e allocatore sono ripristinati al punto del GUARD
    ; La VM è ancora in esecuzione
    MOV.S R1, 0
    RET

Quando un fault avviene dentro un blocco GUARD:

Se trova un GUARD attivo, la VM ripristina:

  • PC → torna all'istruzione dopo GUARD (o all'inizio dell'handler di fault)
  • SP → ripristina lo stack al punto del GUARD (nessuna perdita)
  • Allocatore scratch → ripristina il punto di allocazione

Risultato: un fault non crasha la VM. Non crasha il sistema. È un evento come un altro — si gestisce, si logga, si recupera.

3.8 Caso concreto: un sistema di acquisizione a 3 eventi

Mettiamo insieme i concetti in un esempio reale. Un sistema che:

  1. Legge un sensore ogni 10ms
  2. Invia dati via UART ogni 100ms
  3. Elabora comandi ricevuti via UART
.VECTOR TICK_10MS(flags:FLG), read_sensor
.VECTOR TICK_100MS(flags:FLG), send_data
.VECTOR UART_RX(buf:PTR, len:U16), process_command

; --- Evento 1: lettura sensore (10ms) ---
read_sensor:
    MARK
    ALLOC R1, 4          ; buffer temporaneo nello scratch
    SYSCALL SYS_ADC_READ ; R1 = valore sensore
    ST32 R1, last_value  ; salva in variabile globale (frame)
    FREE
    RET

; --- Evento 2: invio dati (100ms) ---
send_data:
    MARK
    LD32 R1, last_value
    ALLOC R2, 64         ; buffer per pacchetto
    SYSCALL SYS_FORMAT_PACKET
    SYSCALL SYS_UART_SEND
    FREE
    RET

; --- Evento 3: comandi UART (arrivo asincrono) ---
process_command:
    ; R2 = puntatore ai dati ricevuti (in frame, pinnato da syscall)
    ; R3 = lunghezza
    LD8 R1, 0(R2)        ; primo byte = comando
    CMP.S R1, CMD_CALIBRA
    BNE @skip_calibra
    SYSCALL SYS_CALIBRA_SENSORE
@skip_calibra:
    SYSCALL SYS_RELEASE_UART_BUF  ; unpinna il buffer
    RET

Analizziamo il determinismo:

Evento Budget Peggior caso Esito
TICK_10MS 5000 istruzioni ~50 istruzioni ✅ Sempre in tempo
TICK_100MS 5000 istruzioni ~200 istruzioni ✅ Sempre in tempo
UART_RX 2000 istruzioni ~100 istruzioni ✅ Sempre in tempo

Il 99% del tempo CPU è inattivo — la VM yielda per slicer esaurito (nessun evento da processare) o per YIELD esplicito. I tre eventi non competono mai per la CPU: c'è sempre abbastanza budget per tutti.

3.9 Cosa NON è determinista in Caldeira

Onestà intellettuale: Caldeira non rende l'intero sistema deterministico. Resta fuori dal suo controllo:

  • Il codice C delle syscall. Se la syscall fa un malloc che fallisce, la VM non può proteggerti. Il determinismo di Caldeira copre il bytecode, non l'host.
  • L'hardware esterno. Un sensore che impiega 10ms invece di 1ms non è colpa della VM. Ma la syscall che lo interroga può yieldare — e la VM riprende senza perdere un colpo.
  • Il dispatcher host. La VM è cooperativa. Se l'host decide di non chiamare la VM per 50ms, la VM non può farci nulla. Ma una volta chiamata, esegue in modo deterministico.

Caldeira ti dà determinismo dove conta: nell'esecuzione del tuo codice applicativo. Quello che sta intorno (syscall, host loop) è tuo compito rendere altrettanto prevedibile.

4. La memoria come territorio

"Un sistema senza confini di memoria non è un sistema. È un ammasso di bit che prima o poi collasserà su sé stesso."

4.1 Il problema dei confini

Nell'embedded tradizionale, la memoria è una distesa senza recinti. Il codice C vede un unico spazio di indirizzamento lineare: può leggere e scrivere ovunque. Un puntatore può puntare a una variabile, a un registro hardware, a una struttura di sistema, o a un'altra funzione. Non c'è modo di distinguere.

int valore_sensore = 0;
int* ptr = &;valore_sensore;

ptr[0] = 42;    // ok: è la variabile
ptr[100] = 0;   // ???
ptr[-1000] = 0; // ???

Il linguaggio C non ha confini. I confini li devi mettere tu, con la disciplina. E la disciplina, su un progetto di 200.000 righe con 10 sviluppatori, non è una strategia di affidabilità.

Caldeira VM affronta il problema in modo strutturale: non c'è un unico spazio di memoria. Ci sono tre regioni distinte, ciascuna con il suo scopo, i suoi permessi e le sue garanzie.

Indirizzi logici VM
┌──────────────────────┐  ▲
│    R_BYTECODE        │  │ 0x00000000
│    (read-only)       │  │
│                      │  │
├──────────────────────┤  │
│    R_SHARED          │  │
│    (frame arena)     │  │
│    (read-write)      │  │
├──────────────────────┤  │
│    R_PRIVATE         │  │
│    (scratch + stack) │  │
│    (read-write)      │  │
└──────────────────────┘  ▼ 0xFFFFFFFF

Non c'è una regione "fai quello che vuoi". Ci sono tre regioni, ognuna con regole precise. La VM controlla ogni accesso. Se un'istruzione ST32 prova a scrivere nel bytecode, la VM genera un fault. Se prova a leggere oltre i limiti della regione, fault. Se il puntatore è misallineato, fault.

(Nella pratica, le regioni sono separate da intervalli di indirizzi logici. La protezione viene dall'ordine delle verifiche: il bytecode viene controllato per primo (read-only), poi la memoria privata, poi la memoria condivisa. Questo garantisce l'isolamento senza richiedere indirizzi fisici separati.)

Non è "speriamo che lo sviluppatore non sbagli". È strutturalmente impossibile sbagliare. La VM non te lo permette.

4.2 Regione 1: Bytecode — la memoria che non cambia mai

La prima regione contiene il codice del programma: le istruzioni .lava che la VM esegue.

Caratteristiche:

Proprietà Valore
Posizione fisica Flash (o RAM, a seconda del target)
Accesso Sola lettura
Contiene Codice bytecode, class descriptor, vettori evento
Dimensione Tipicamente 8-64 KB
Ciclo di vita Dall'avvio del sistema al suo spegnimento

Il bytecode è read-only. Non perché la VM lo protegga a livello hardware (sui MCU senza MMU non può), ma perché la VM controlla ogni accesso. Se un'istruzione prova a scrivere in questa regione, la VM genera FAULT_INVALID_WRITE.

Tradotto: se il tuo programma prova a scrivere sopra sé stesso, la VM lo ferma. Sempre. Non "se il compilatore ha abilitato gli header di controllo". Sempre.

4.2.1 Cosa c'è nel bytecode

Il bytecode non contiene solo codice. Contiene anche:

  • Vettori evento: la tabella degli handler (all'inizio del file .lava)
  • Class descriptor: le tabelle dei metodi delle classi (usate da CALLM)
  • Dati statici: costanti, stringhe, tabelle pre-calcolate
  • Metadata: informazioni sulla memoria e sulle classi per l'inizializzazione
Offset  │ Contenuto
────────┼─────────────────────────
0x0000  │ Vettori evento (N x 4 byte, uno per evento)
0x0100  │ Metadata: class table ptr, class count, split memoria
0x0140  │ Dati statici (.STATIC)
0x0200  │ Codice programma
...     │ ...
0x8000  │ Class Descriptor 0
0x8010  │ Class Descriptor 1

La class table (in flash) contiene i puntatori ai descriptor. Questo significa che la struttura delle classi è fissa nel bytecode. Non puoi creare nuove classi a runtime — cosa che, in un sistema embedded deterministico, è una caratteristica, non un limite.

4.3 Regione 2: Frame Arena — la memoria che sopravvive

La seconda regione è il Frame Arena: la memoria condivisa tra eventi e tra VM. È la "memoria persistente" del sistema.

4.3.1 Caratteristiche

Proprietà Valore
Posizione fisica RAM
Accesso Lettura e scrittura
Contiene Oggetti persistenti, buffer, dati condivisi
Gestione Page allocator con MARK.FR/FREE.FR
Dimensione Tipicamente 60-80% della RAM disponibile
Condivisione Tra eventi E tra VM diverse (in configurazione multi-VM)

4.3.2 Allocazione

Lo frame si alloca con le istruzioni NEW.FR (per oggetti) e ALLOC.FR (per buffer raw):

ALLOC.FR R1, 64    ; alloca 64 byte nel frame, R1 = indirizzo
NEW.FR R1, 2       ; alloca istanza classe 2 nel frame

Internamente, il frame è diviso in pagine di dimensione fissa (tipicamente 64 byte):

Ogni pagina ha un owner: un numero che identifica il gruppo MARK.FR a cui appartiene. Quando fai FREE.FR, tutte le pagine del gruppo corrente vengono liberate collettivamente — non una per una, ma tutte insieme.

MARK.FR  → crea gruppo 1
ALLOC.FR R1, 128  → R1 punta alla pagina 5 (owner = 1)
ALLOC.FR R2, 64   → R2 punta alla pagina 7 (owner = 1)
FREE.FR  → libera tutte le pagine con owner = 1
           → pagina 5 libera, pagina 7 libera
           → R1 e R2 non sono più validi

Questo è il pattern regionale: non liberi singoli oggetti, ma intere regioni di allocazione. È come un malloc senza free — la deallocazione è collettiva e O(1).

4.3.3 Perché è determinista

Perché non c'è frammentazione.

Un malloc/free tradizionale frammenta la memoria: blocchi di diverse dimensioni lasciano buchi che non possono essere riutilizzati. Col tempo, la memoria diventa un formaggio svizzero — tanti buchi piccoli, nessuno abbastanza grande per un'allocazione grande, ma malloc fallisce.

Con MARK.FR/FREE.FR, la memoria è un campo di battaglia con plotoni: ogni plotone (gruppo) occupa un'area contigua. Quando il plotone viene congedato (FREE.FR), tutta l'area torna libera. Niente buchi. Niente frammentazione.

Stato iniziale:
[░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░]  tutto libero

Dopo MARK.FR + 3 allocazioni:
[████ gruppo 1 ████][░░░░░░░░░░░░]  gruppo 1 occupa N pagine

Dopo MARK.FR + 1 allocazione:
[████ gruppo 1 ████][█████ gruppo 2 ██][░░░░░░░]

Dopo FREE.FR (gruppo 2):
[████ gruppo 1 ████][░░░░░░░░░░░░░░░░]  nessun buco!

Dopo FREE.FR (gruppo 1):
[░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░]  tutto torna libero

La memoria è un pacco di fogli: ne usi alcuni, poi li butti via tutti insieme. Non cerchi mai un foglio libero in mezzo a fogli usati. È sempre contigua.

4.4 Regione 3: Arena Privata — la memoria che non lascia traccia

La terza regione è l'arena privata di ogni VM: scratch + stack. È la memoria temporanea per eccellenza.

4.4.1 Caratteristiche

Proprietà Valore
Posizione fisica RAM
Accesso Lettura e scrittura
Contiene Allocazioni temporanee, stack CALL/RET
Gestione Bump pointer per scratch, SP per stack
Condivisione Nessuna — è privata per VM
Ciclo di vita Un evento alla volta

La struttura:

Indirizzi alti
┌──────────────────────┐  ← inizio memoria privata
│                      │
│      STACK (CALL)    │  ← cresce verso il basso
│     cresce verso     │
│     il basso         │
├──────────────────────┤  ← base dello stack
│                      │
│      SCRATCH         │  ← cresce verso l'alto
│     (ALLOC/MARK)     │
│                      │
├──────────────────────┤  ← fine area scratch
│      .STATIC         │  ← dati statici (copiati dal bytecode all'avvio)
└──────────────────────┘  ← 0 (indirizzo logico)

Stack e scratch crescono l'uno verso l'altro. Se collidono, la VM genera FAULT_STACK_OVERFLOW. Il sistema non crasha — la VM si ferma e notifica il fault.

4.4.2 Ciclo di vita di uno scratch

Ogni evento parte con lo scratch resettato al valore salvato all'inizio dell'evento. Quando un evento termina, tutta la memoria che ha allocato nello scratch scompare. Non c'è free. Non c'è garbage collection. C'è solo un puntatore che torna indietro.

Prima dell'evento:
  allocatore = 0x2000

Durante l'evento:
  ALLOC 32 → allocatore = 0x2020
  ALLOC 64 → allocatore = 0x2060
  MARK
  ALLOC 16 → allocatore = 0x2070
  FREE     → allocatore = 0x2060

Fine evento:
  allocatore = 0x2000 (torna al valore iniziale)
  
  Tutto ciò che è stato allocato tra 0x2000 e 0x2060 è ora libero.
  In un colpo solo. O(1). Zero frammentazione.

4.4.3 Perché due arene? Non bastava una sola?

È la domanda giusta. Potremmo avere una sola arena e usare MARK/FREE per tutto. Ma la separazione in privata e condivisa risolve un problema fondamentale:

  • Lo scratch è privato per VM: un'allocazione temporanea di VM1 non può corrompere VM2
  • Il frame è condiviso: VM1 e VM2 possono comunicare attraverso buffer condivisi

Se ci fosse una sola arena, o sarebbe privata (impossibile comunicare tra VM) o condivisa (un evento potrebbe corrompere lo scratch di un altro).

Le due arene danno il meglio di entrambi i mondi: isolamento per le operazioni temporanee, condivisione per i dati persistenti.

4.5 Il sistema di protezione a runtime

La VM controlla ogni singolo accesso alla memoria:

  1. L'indirizzo appartiene a una regione?
  2. La regione permette la scrittura (per le ST)?
  3. L'accesso non supera il limite della regione?

Il risultato è che è strutturalmente impossibile scrivere dove non si deve.

4.6 Caso d'uso: pipeline di elaborazione eventi

Mettiamo insieme le tre regioni in un esempio concreto: una pipeline di elaborazione dati che riceve un pacchetto, lo analizza, lo archivia e lo ritrasmette.

.VECTOR UART_RX(buf:PTR, len:U16), process_packet

.VECTOR TICK_10MS(flags:FLG), housekeeping

; --- Elaborazione pacchetto ---
process_packet:
    ; R2 = puntatore al buffer (nel frame, pinnato da syscall)
    ; R3 = lunghezza

    ; 1. Alloca buffer di elaborazione nello scratch (temporaneo)
    MARK
    ALLOC R4, 256           ; buffer temporaneo

    ; 2. Copia il pacchetto dal frame allo scratch
    ;    (lo frame resterà pinnato finché la syscall non lo rilascia)
    LD32 R5, 0(R2)          ; legge header dal frame
    ST32 R4, R5             ; copia in scratch (elaborazione sicura)

    ; 3. Elabora nel buffer temporaneo
    SYSCALL SYS_CRC_CHECK
    CMP R1, 0
    BEQ @packet_corrupto

    ; 4. Scrivi risultato nel frame (persistente)
    SYSCALL SYS_SAVE_TO_ARCHIVE   ; usa R2 (frame) come input

    ; 5. Sblocca il buffer UART (syscall fa unpin)
    SYSCALL SYS_RELEASE_UART_BUF

    ; 6. Libera scratch
    FREE
    RET

@packet_corrupto:
    SYSCALL SYS_LOG_ERROR
    SYSCALL SYS_RELEASE_UART_BUF
    FREE
    RET

; --- Housekeeping periodico ---
housekeeping:
    ; Non serve MARK/FREE: non alloca nulla (usa solo registri)
    SYSCALL SYS_READ_TEMP
    SYSCALL SYS_UPDATE_DISPLAY
    RET

Analizziamo il flusso della memoria:

Fase Regione Cosa succede
Ricezione UART Frame (shared) La syscall UART alloca e pinna un buffer nel frame
process_packet Scratch (private) ALLOC 256 byte per elaborare il pacchetto
CRC check Scratch Legge e scrive solo nel buffer scratch
Archiviazione Frame Scrive il risultato nel database nel frame
Sblocco UART Frame La syscall unpinna il buffer UART
FREE Scratch 256 byte liberati in un colpo solo
housekeeping — Non alloca nulla — usa solo registri

Nessuna allocazione dinamica residua. Nessuna frammentazione. Nessuna possibilità che un evento corrompa lo scratch dell'altro.

4.7 Il confronto con la memoria tradizionale

Aspetto C nudo + malloc/free Caldeira VM
Allocazione malloc — tempo variabile ALLOC — O(1)
Deallocazione free — tempo variabile FREE — O(1)
Frammentazione Si accumula nel tempo Non esiste
Protezione lettura Nessuna Controllo regione per ogni accesso
Protezione scrittura Nessuna Controllo regione + read-only per bytecode
Overflow Buffer overflow silenzioso FAULT su accesso oltre limite
Allocazione tra eventi Malloc globale, race condition Arena privata per VM, resettata per evento
Comunicazione inter-VM Memoria condivisa non protetta Frame condiviso, accesso controllato
Debug valgrind (solo PC), ispezione manuale FAULT su ogni violazione + GDB stub

Il costo del controllo è tangibile: ogni accesso alla memoria viene validato. Ma è un costo fisso e prevedibile, e in cambio elimina intere categorie di bug: buffer overflow, use-after-free, double free, scrittura in read-only.

4.8 Pattern: come scegliere la regione giusta

Una regola pratica per decidere dove mettere i dati:

Il dato serve SOLO durante questo evento?
├── Sì → SCRATCH (ALLOC + MARK/FREE)
│
├── Il dato deve sopravvivere alla fine dell'evento?
│   ├── È usato SOLO da questa VM?
│   │   ├── Sì → dipende: se piccolo e statico, .STATIC; se dinamico, FRAME
│   │   └── No (condiviso tra VM) → FRAME
│   │
│   Il dato può essere ricreato?
│   ├── Sì → SCRATCH (ricrea ogni evento)
│   └── No → FRAME (persistente)
│
Il dato è di configurazione (non cambia)?
└── Sì → BYTECODE (flash, read-only)

Esempi concreti

Dato Regione Perché
Buffer di elaborazione pacchetto Scratch Serve solo durante l'handler UART_RX
Buffer DMA per ADC Frame Deve sopravvivere allo yield mentre l'ADC converte
Variabile contatore Frame Deve sopravvivere tra un tick e l'altro
Stringa di log Bytecode Non cambia mai, può stare in flash
Archivio sensori Frame Condiviso tra evento lettura e evento trasmissione
Parametri di calibrazione Bytecode (o Frame se modificabili) Se fissi: flash. Se regolabili: frame

4.9 I limiti

Onestà, di nuovo.

Le tre regioni coprono la maggior parte dei casi d'uso, ma non tutti:

  • Strutture dati dinamiche complesse (liste linkate, alberi, grafi) non sono il punto di forza del modello regionale. In un sistema embedded deterministico, spesso non servono, ma se servono, devi gestirle manualmente nel frame.
  • Dati grandi (es. buffer audio di 100 KB) potrebbero non entrare in una singola regione se il frame è piccolo. In tal caso, si allocano nel frame e si passa il puntatore.
  • Memoria condivisa tra VM e host C: la syscall vede il frame condiviso tramite caldeira_get_buffer. Ma non c'è un meccanismo automatico di sincronizzazione — tocca alla syscall gestire la coerenza.

5. Oggetti, metodi e VTable in flash

"L'object-oriented programming è una buona idea. Il C++ è una cattiva implementazione. Caldeira è un tentativo di fare le cose per bene." — adattato liberamente

5.1 OO su un microcontrollore? Ma dai.

Quando si parla di "object-oriented" nell'embedded, la reazione è spesso un misto di scetticismo e nausea. Giustificato. Il C++ embedded ha lasciato cicatrici:

  • RTTI (Run-Time Type Information) che occupa flash senza motivo
  • Template che esplodono in codice binario gigantesco
  • Eccezioni che richiedono un runtime complesso e memory overhead
  • Ereditarietà multipla che rende le vtable un labirinto
  • Virtual dispatch indiretto che confonde il branch predictor

E poi c'è la narrativa: "l'OO è troppo lento per l'embedded", "le classi sono solo zucchero sintattico", "io uso struct e puntatori a funzione, è la stessa cosa".

Non è la stessa cosa. E l'OO non è lento per l'embedded — è il C++ che è lento per l'embedded. Caldeira fa OO embedded in modo diverso:

  1. Class descriptor in flash — la struttura della classe è nel bytecode, non in RAM
  2. Istanze in RAM — i dati dell'oggetto sono nella frame arena
  3. CALLM — un'unica istruzione per chiamata di metodo virtuale
  4. Niente runtime type info — il class ID è nell'header dell'oggetto (16 bit)
  5. Niente ereditarietà multipla — interfacce semplici, composizione invece di gerarchie
  6. Niente allocazione dinamica per gli oggetti — NEW/NEW.FR usano le arene

5.2 Anatomia di un oggetto Caldeira

Un oggetto Caldeira in memoria occupa solo l'header (4 byte) + i campi dati. L'esempio con 3 campi qui sotto usa 8 byte totali. Niente header complesso, niente vtable in RAM, niente allocazioni extra:

┌──────────────┬──────────────┐
│  size (16)   │  class_id    │  ← header (4 byte, 1 word)
│              │    (16)      │
├──────────────┴──────────────┤
│                             │
│   field_0                   │  ← primo campo (es. state:U8, 1 byte)
│   field_1                   │  ← secondo campo (es. brightness:U8, 1 byte)
│   ...                       │
│   field_n                   │
│                             │
└─────────────────────────────┘

Header: una singola word di 32 bit divisa in due metà:

  • Bit [31:16]: instance_size — dimensione totale dell'oggetto in byte (allineata a 4)
  • Bit [15:0]: class_id — identificativo della classe (usato da CALLM per il dispatch)

Campi: subito dopo l'header, nello stesso blocco di memoria. L'offset di ogni campo è noto a compile-time, definito dal .FIELD nel sorgente .clasto.

; Definizione classe
.CLASS LED
    .FIELD state:U8         ; offset 4 (subito dopo header 4 byte)
    .FIELD brightness:U8    ; offset 5
    .FIELD pin:U16          ; offset 6 (allineato a 2)
.END_CLASS

L'oggetto in memoria:

Offset  │ Dimensione │ Contenuto
────────┼────────────┼──────────
0       │ 4 byte     │ [instance_size=8][class_id=0]
4       │ 1 byte     │ state
5       │ 1 byte     │ brightness
6       │ 2 byte     │ pin
────────┼────────────┼──────────
        │ 8 byte     │ totale

L'header è volutamente minimale. Non c'è puntatore alla vtable. Non c'è tipo runtime. Non c'è reference count. Solo size e class_id. Il resto è nel class descriptor in flash.

5.3 Il Class Descriptor in flash

Ogni classe definita in .clasto genera un Class Descriptor nel bytecode (in flash/ROM):

┌──────────────────────────────────────┐
│  [ instance_size | method_count ]    │  ← prima word del descriptor
├──────────────────────────────────────┤
│  method_addr_0                       │  ← indirizzo del primo metodo
│  method_addr_1                       │  ← indirizzo del secondo metodo
│  ...                                 │
│  method_addr_N                       │
└──────────────────────────────────────┘

Il descriptor è nel bytecode per una ragione precisa: non occupa RAM. Non deve essere caricato, non deve essere inizializzato. È già lì, nella flash, pronto all'uso.

Dove si trova il descriptor? La Class Table (anche lei in flash) contiene un puntatore per ogni classe:

│  desc_offset_0   ← offset nel bytecode del descriptor classe 0
│  desc_offset_1   ← offset nel bytecode del descriptor classe 1
│  ...                                 │
│  desc_offset_N                       │
└──────────────────────────────────────┘

5.4 CALLM: l'istruzione che cambia tutto

CALLM Rd, Imm è l'istruzione centrale dell'OO in Caldeira. Fa tre cose in una:

  1. Carica l'oggetto in R13 (this)
  2. Risolve il metodo virtuale tramite class table + descriptor
  3. Chiama il metodo (push PC, salta al target)
; Chiama il metodo Init (indice 0) sull'oggetto in R1
CALLM R1, 0

; Dopo CALLM:
; R13 = R1 (this, caricato automaticamente)
; PC  = indirizzo del metodo Init
; SP  = decrementato di 4 (PC salvato)

A differenza di C++, dove il virtual dispatch passa attraverso una vtable in RAM (con tutti i problemi di puntatori corrotti), in Caldeira la risoluzione è sempre in flash, sempre sicura. Non puoi corrompere la vtable perché non c'è — è tutta nel bytecode read-only.

5.4.1 Modi di indirizzamento

CALLM supporta due forme:

; Forma registro: CALLM R1, method_idx
; L'oggetto è in R1, R13 = R1
CALLM R1, 0

; Forma memoria: CALLM offset(Rs), method_idx
; L'oggetto è caricato da memoria (es. da un array di puntatori)
CALLM 0(R8), 0   ; R13 = mem[R8 + 0]
CALLM 4(R8), 1   ; R13 = mem[R8 + 4]

La seconda forma è particolarmente utile per array polimorfi:

; Array di oggetti LED (puntatori)
; R8  = base dell'array
; R9  = indice corrente

; Chiama Init sull'oggetto i-esimo
CALLM 0(R8), 0       ; Init sul primo
CALLM 4(R8), 0       ; Init sul secondo (offset 4 perché ogni puntatore è 4 byte)

5.5 Interfacce: il contratto senza implementazione

Caldeira supporta anche le interfacce — classi senza campi, solo firme di metodi:

.INTERFACE Sensor
    .METHOD read(pin:U16) ->; U16
    .METHOD calibrate()
.END_INTERFACE

Una classe concreta può implementare un'interfaccia:

.CLASS TemperatureSensor IMPLEMENTS Sensor
    .FIELD pin:U16
    .FIELD last_value:U16

    .METHOD read(pin:U16) ->; U16
        MOV.S R1, R2       ; R2 = pin passato come argomento
        SYSCALL SYS_ADC_READ
        ST16 R1, last_value(R13)
        RET

    .METHOD calibrate()
        MOV.S R1, 100
        SYSCALL SYS_ADC_CALIBRATE
        RET
.END_CLASS

Quando una classe dichiara IMPLEMENTS Interfaccia, l'assemblatore:

  1. Verifica che tutti i metodi dell'interfaccia siano presenti nella classe
  2. Genera una VTable che rispetta l'ordine dei metodi dell'interfaccia
  3. Segnala errore a compile-time se un metodo manca o ha firma diversa

Il vantaggio: il polimorfismo è controllato staticamente. Se dichiari di implementare Sensor, devi avere tutti i metodi di Sensor. Non c'è rischio di dimenticare un override.

; Array polimorfo di sensori
; Ogni elemento è un puntatore a un oggetto che implementa Sensor
; Possono essere TemperatureSensor, PressureSensor, ecc.

main:
    NEW R1, 0              ; TemperatureSensor
    ST32 R1, 0(R8)        ; array[0] = temperature
    NEW R1, 1              ; PressureSensor
    ST32 R1, 4(R8)        ; array[1] = pressure

loop:
    CALLM 0(R8), 0         ; read() sul primo sensore (qualunque classe sia)
    CALLM 4(R8), 0         ; read() sul secondo sensore
    JMP loop

La VM non sa (e non le interessa) che tipo di oggetto c'è in 0(R8). Legge il class_id dall'header, cerca nella class table, salta al metodo giusto. Polimorfismo. Su un ESP32.

5.6 NEW e NEW.FR: creare oggetti

Creare un oggetto in Caldeira è un'istruzione, non una funzione:

; NEW: alloca nello scratch (temporaneo)
NEW R1, 0          ; R1 = nuova istanza classe 0 (nello scratch)

; NEW.FR: alloca nel frame (persistente)
NEW.FR R2, 0       ; R2 = nuova istanza classe 0 (nel frame)

Il primo argomento è il registro di destinazione (il puntatore all'oggetto). Il secondo è il Class ID (noto a compile-time, generato dall'assemblatore).

NEW R1, 0           ; R1 = nuovo oggetto classe 0

5.7 Campi: accesso via LD/ST con offset

I campi di un oggetto non hanno sintassi speciale — si accedono con le normali LD/ST usando R13 (this) come base:

.METHOD Init
    ; R13 = this
    MOV.S R1, 0
    ST8 R1, 4(R13)      ; state = 0 (offset 4: subito dopo header)
    MOV.S R1, 255
    ST8 R1, 5(R13)      ; brightness = 255 (offset 5)
    RET

L'offset di ogni campo è calcolato dall'assemblatore tenendo conto dell'allineamento opzionale (VM_FIELD_REORDERING). Se il flag è attivo, l'assemblatore riordina i campi per dimensione (dal più grande al più piccolo) per minimizzare il padding.

; Campi dichiarati:
.FIELD valore:U16      ; 2 byte
.FIELD flag:U8         ; 1 byte
.FIELD count:U32       ; 4 byte

; Con reordering, l'ordine in memoria diventa:
; offset 4: count (U32, 4 byte)
; offset 8: valore (U16, 2 byte)
; offset 10: flag (U8, 1 byte)
; offset 11: fine (3 byte di padding → 12 totali)

L'utente del DSL (o lo sviluppatore assembly) non deve preoccuparsi dell'ordine — usa sempre il nome del campo tramite la direttiva .ABI o le costanti generate dall'assemblatore. L'offset reale è un dettaglio del compilatore.

5.8 Un esempio completo: sistema di LED

Mettiamo tutto insieme in un esempio reale.

; ---------- Definizione classi ----------
.CLASS LED
    .FIELD state:U8            ; 0=off, 1=on (offset 4)
    .FIELD pin:U8             ; pin GPIO (offset 5)
    .FIELD brightness:U8       ; 0-255 (offset 6)

    .METHOD Init(pin:U8)
        ST8 R2, 5(R13)         ; this.pin = pin
        MOV.S R1, 0
        ST8 R1, 4(R13)         ; this.state = 0
        MOV.S R1, 255
        ST8 R1, 6(R13)         ; this.brightness = 255
        RET

    .METHOD TurnOn()
        MOV.S R1, 1
        ST8 R1, 4(R13)         ; this.state = 1
        LD8 R1, 5(R13)         ; R1 = this.pin
        SYSCALL SYS_GPIO_ON
        RET

    .METHOD TurnOff()
        MOV.S R1, 0
        ST8 R1, 4(R13)         ; this.state = 0
        LD8 R1, 5(R13)         ; R1 = this.pin
        SYSCALL SYS_GPIO_OFF
        RET

    .METHOD SetBrightness(level:U8)
        ST8 R2, 6(R13)         ; this.brightness = level
        RET
.END_CLASS

; ---------- Programma principale ----------

    ; Crea 2 LED
    NEW R8, 0                  ; LED 1 (classe 0)
    CALLM R8, 0                ; Init, ma senza pin... 
    ; (In un sistema reale Init riceverebbe il pin da config)

    NEW R9, 0                  ; LED 2 (classe 0)
    CALLM R9, 0                ; Init

    ; Accendi LED1
    CALLM R8, 1                ; TurnOn()

    ; Imposta luminosità LED2
    MOV.S R2, 128
    CALLM R9, 3                ; SetBrightness(128)

    ; Spegni LED1
    CALLM R8, 2                ; TurnOff()
    HALT

Non c'è new in C++. Non c'è class LED : public .... Non c'è allocazione dinamica. Solo un'istruzione (NEW), una chiamata (CALLM), e un oggetto con i suoi metodi.

6. Metaprogrammazione e DSL

"Ogni linguaggio assembly è sufficiente per scrivere qualsiasi programma. La vera domanda è: quanto è faticoso?"

6.1 Il problema della ripetizione

L'assembly .clasto è potente ma verboso. Ripetere la stessa sequenza di istruzioni piú e piú volte è noioso, fragile, e nasconde l'intenzione dietro il meccanismo.

L'assemblatore Caldeira offre direttive compile-time (.FOR, .MACRO, .IF, .CONST) per generare codice a compile-time — sono spiegate in dettaglio nella documentazione tecnica. Ma c'è un salto piú grande: creare un linguaggio dedicato che viene compilato in assembly .clasto.

6.2 Esempio concreto: un DSL per pattern LED

Immagina di voler descrivere un pattern di lampeggio LED in un linguaggio semplice:

PATTERN blink
  LED ON
  WAIT 500
  LED OFF
  WAIT 500
REPEAT 3

Questo è un DSL: poche parole, chiare, che descrivono cosa fare, non come farlo passo-passo.

Scriviamo un compilatore in Python che traduce questo DSL in assembly .clasto:

def compile_led_pattern(source: str) -> str:
    lines = source.strip().split('\n')
    name = ""
    repeat = 1
    steps = []
    
    for line in lines:
        line = line.strip()
        if line.startswith('PATTERN'):
            name = line.split()[1]
        elif line.startswith('REPEAT'):
            repeat = int(line.split()[1])
        elif line == 'LED ON':
            steps.append('    MOV.S R1, 1\n    SYSCALL SYS_GPIO_WRITE')
        elif line == 'LED OFF':
            steps.append('    MOV.S R1, 0\n    SYSCALL SYS_GPIO_WRITE')
        elif line.startswith('WAIT'):
            ms = line.split()[1]
            steps.append(f'    MOV.S R1, {ms}\n    SYSCALL SYS_DELAY_MS')
    
    asm = f'''; Generato da compilatore DSL: {name}
.CONST LED_PIN 0

.VECTOR EVT_RESET(flags:FLG), main
main:
    MOV.S R2, LED_PIN
    MOV.S R3, 1          ; output
    SYSCALL SYS_GPIO_SET_DIR
    
    .FOR i, 0, {repeat}
'''
    for step in steps:
        asm += f'{step}\n'
    asm += '    .END_FOR\n    HALT\n'
    return asm

Dato il sorgente DSL, produce:

; Generato da compilatore DSL: blink
.CONST LED_PIN 0
.VECTOR EVT_RESET(flags:FLG), main
main:
    MOV.S R2, LED_PIN
    MOV.S R3, 1
    SYSCALL SYS_GPIO_SET_DIR
    .FOR i, 0, 3
    MOV.S R1, 1
    SYSCALL SYS_GPIO_WRITE
    MOV.S R1, 500
    SYSCALL SYS_DELAY_MS
    MOV.S R1, 0
    SYSCALL SYS_GPIO_WRITE
    MOV.S R1, 500
    SYSCALL SYS_DELAY_MS
    .END_FOR
    HALT

Il flusso è semplice:

DSL sorgente           →  compilatore DSL    →  .clasto    →  clasto    →  .lava    →  lava
(blink.txt)               (Python breve)        (assembly)     (assembla)    (bytecode)  (esegue)

6.3 Perché ha senso

Il compilatore DSL fa due cose:

  1. Nasconde la complessità — l'utente scrive LED ON e WAIT 500, non deve sapere quali registri usare o come si chiama la syscall
  2. Rende esplicita l'intenzione — PATTERN blink dice cosa fa, .FOR i, 0, 3 dice quante volte

Tutto il resto — determinismo, isolamento, scheduling — lo fa la VM, gratis.

7. Syscall: il ponte tra VM e mondo reale

"La VM è una bolla di determinismo. Le syscall sono le finestre attraverso cui la bolla tocca il mondo reale. La qualità del sistema è la qualità delle sue finestre."

8.1 Il confine tra due mondi

La VM Caldeira è un ambiente determinista, isolato, prevedibile. Ogni evento ha un budget di istruzioni. Ogni accesso alla memoria è controllato. Ogni fault è recuperabile. È una bolla di sicurezza.

Ma la bolla non vive nel vuoto. Deve interagire con il mondo reale:

  • Leggere un pin GPIO
  • Scrivere su un bus I²C
  • Avviare una conversione ADC
  • Inviare un pacchetto UART
  • Attendere un interrupt hardware

Queste operazioni non sono deterministiche. Una lettura I²C può impiegare 1ms o 10ms a seconda della risposta del dispositivo. Una scrittura su flash può richiedere 5ms. Un'attesa di un interrupt può durare un tempo imprevedibile.

Il confine tra il mondo deterministico della VM e il mondo imprevedibile dell'hardware è rappresentato dalle syscall. Sono il ponte, ma anche il filtro: le syscall proteggono la VM dall'imprevedibilità dell'hardware e proteggono l'hardware dagli errori della VM.

┌──────────────────────────────────────────────┐
│              VM (bytecode .lava)              │
│  • Determinista                              │
│  • Budget di istruzioni                      │
│  • Memoria controllata                       │
│  • Fault recuperabili                        │
├──────────────────────────────────────────────┤
│              SYSCALL handler (C)             │
│  • Può yieldare (se serve attesa)            │
│  • Può fallire (ritorna errore in R1)        │
│  • Può postare eventi (fire_event)           │
├──────────────────────────────────────────────┤
│              HAL / Driver (C)                │
│  • DMA, interrupt, registri hardware         │
│  • Non deterministico                        │
│  • Non protetto (l'hardware non mente mai)   │
└──────────────────────────────────────────────┘

La VM non parla direttamente con l'hardware. Parla con le syscall. E le syscall parlano con l'HAL. Questo strato di separazione è ciò che rende Caldeira portabile, sicura e testabile.

8.2 Anatomia di una syscall

Una syscall è, tecnicamente, una funzione C con questa firma:

void mia_syscall(VMContext* vm);
  • Input: riceve un handle opaco per la VM chiamante
  • Output: non c'è return — il risultato si scrive tramite CALDEIRA_RETURN
  • Side effects: può leggere/scrivere memoria VM, postare eventi, yieldare, accedere all'hardware

Tutte le syscall sono registrate in una tabella a 256 slot (VMSyscallTable). Il bytecode le chiama per ID:

MOV.S R1, 34         ; pin = 34 (primo argomento)
SYSCALL 0x90         ; chiama syscall ID 0x90 (sys_adc_read)
; R1 = valore letto dall'ADC

8.2.1 Cosa può fare una syscall

Operazione Come Esempio
Leggere argomenti CALDEIRA_ARG_1(vm) uint32_t pin = CALDEIRA_ARG_1(vm);
Scrivere risultato CALDEIRA_RETURN(vm, val) CALDEIRA_RETURN(vm, 0);
Accedere memoria VM caldeira_get_u32ptr(vm, addr) uint32_t* p = caldeira_get_u32ptr(vm, addr);
Yieldare (attesa) caldeira_yield(vm, resume_id) caldeira_yield(vm, 1);
Postare evento caldeira_fire_event(vm, id, a1, a2, a3) caldeira_fire_event(vm, EVT_UART_DONE, buf, len, 0);
Proteggere buffer caldeira_pin_frame(vm, addr, len) caldeira_pin_frame(vm, buf, 1024);
Impostare fault caldeira_set_fault(vm, code) caldeira_set_fault(vm, CALDEIRA_FAULT_INVALID_READ);
Leggere stato VM caldeira_get_state(vm) if (caldeira_get_state(vm) == CALDEIRA_STATE_FAULT) ...

8.2.2 Cosa NON può fare una syscall

  • Non può corrompere la memoria della VM — la VM controlla ogni scrittura
  • Non può bloccare la CPU per sempre — se yielda, la VM continua con altri eventi
  • Non può accedere ai registri della VM se non tramite le API fornite
  • Non può chiamare altre syscall — non è reentrante

8.3 Pattern sincrono: chiama e attendi

La syscall più semplice: riceve input, produce output, termina subito.

#include ";caldeira.h"

// syscall 0x90: sys_adc_read(pin) ->; value
static void sys_adc_read(VMContext* vm) {
    uint32_t pin = CALDEIRA_ARG_1(vm);    // R1 = pin number

    if (pin >;= MAX_ADC_PINS) {
        CALDEIRA_RETURN(vm, 0xFFFFFFFF);    // errore: pin non valido
        return;
    }

    uint32_t value = hal_adc_read(pin);     // chiama HAL (C nudo)
    CALDEIRA_RETURN(vm, value);             // R1 = risultato
}

Dal bytecode:

MOV.S R1, 34
SYSCALL 0x90        ; R1 = adc_read(34)
; R1 contiene il valore letto (o 0xFFFFFFFF se errore)

Il contratto: la syscall non yielda mai. La VM riprende immediatamente dopo SYSCALL. Il tempo di risposta è determinato dall'HAL, ma l'impatto sulla VM è nullo — l'istruzione successiva viene eseguita subito.

Questo pattern funziona quando l'operazione hardware è veloce (microsecondi): lettura GPIO, scrittura registro, controllo immediato.

8.4 Pattern asincrono: avvia, yield, riprendi

Quando l'operazione hardware richiede tempo (millisecondi o più), la syscall non deve bloccare la VM. Deve avviare l'operazione, yieldare, e riprendere quando l'operazione è completata.

static void sys_uart_read(VMContext* vm) {
    switch (caldeira_get_resume_id(vm)) {

    case 0:  // Prima chiamata: avvia la lettura asincrona
        uint32_t buf_addr = CALDEIRA_ARG_1(vm);
        uint32_t len      = CALDEIRA_ARG_2(vm);

        // 1. Blocca il buffer nel frame (FREE.FR non lo libererà)
        if (!caldeira_pin_frame(vm, buf_addr, len)) {
            CALDEIRA_RETURN(vm, 0xFFFFFFFF);    // errore: buffer non valido
            return;
        }

        // 2. Ottiene il puntatore host al buffer
        uint8_t* buf = (uint8_t*)caldeira_get_buffer(vm, buf_addr, len);
        if (!buf) {
            CALDEIRA_RETURN(vm, 0xFFFFFFFF);
            return;
        }

        // 3. Avvia la lettura UART in DMA
        hal_uart_read_async(buf, len, &;uart_completion_callback);

        // 4. Yield con resume_id = 1
        caldeira_yield(vm, 1);
        return;  // Mai eseguito al primo giro

    case 1:  // Ripresa: DMA completata
        // Sblocca il buffer nel frame
        caldeira_unpin_frame(vm, CALDEIRA_ARG_1(vm), CALDEIRA_ARG_2(vm));
        CALDEIRA_RETURN(vm, 0);  // successo
        break;
    }
}

Il callback C (host-side, eseguito dall'interrupt UART):

Il flusso completo:

Tempo  │ VM                          │ Host
───────┼─────────────────────────────┼──────────────────
t=0    │ SYSCALL 0x91               │
t=1    │   pin_frame(buf)           │
t=2    │   hal_uart_read_async()    │ → Avvia DMA
t=3    │   caldeira_yield(1)        │
t=4    │ [YIELDED]                  │
t=5    │                            │ DMA in corso...
t=6    │                            │ UART IRQ →
t=7    │                            │   uart_callback()
t=8    │                            │   fire_event(UART_DONE)
t=9    │ VM riprende →              │
t=10   │ SYSCALL 0x91 (ri-eseguita) │
t=11   │   resume_id = 1            │
t=12   │   unpin_frame(buf)         │
t=13   │   R1 = 0                   │
t=14   │ Istruzione successiva      │

Cosa rende questo pattern potente:

  1. La VM non si blocca mai — durante l'attesa (t=4 a t=9), altri eventi possono essere eseguiti
  2. Il buffer è protetto — pin_frame garantisce che FREE.FR non lo liberi
  3. La ripresa è automatica — impl_SYSCALL riavvolge il PC se la syscall yielda
  4. La distinzione è esplicita — caldeira_get_resume_id() dice se è prima chiamata o ripresa

8.5 Pattern differito: avvia, termina, notifica

A volte la syscall non deve aspettare il risultato. Deve solo avviare l'operazione e andarsene. Il risultato arriverà dopo, tramite un evento.

static void sys_send_packet(VMContext* vm) {
    uint32_t data_addr = CALDEIRA_ARG_1(vm);
    uint32_t len       = CALDEIRA_ARG_2(vm);

    // Pinna il buffer (protegge da FREE.FR)
    caldeira_pin_frame(vm, data_addr, len);

    // Avvia la trasmissione
    uint8_t* data = (uint8_t*)caldeira_get_buffer(vm, data_addr, len);
    hal_can_send_async(data, len, &;can_tx_callback);

    // Torna SUBITO — non yielda, non aspetta
    CALDEIRA_RETURN(vm, 0);
}

Il completamento arriva come evento separato:

; Chiamata alla syscall
MOV.S R1, packet_addr
MOV.S R2, 8
SYSCALL 0x92           ; sys_send_packet(packet, 8)
; R1 = 0 (accettato)

; ... altro codice ...

.VECTOR CAN_TX_DONE(buf:PTR, len:U16), on_packet_sent

on_packet_sent:
    ; Il pacchetto è stato inviato con successo
    ; R2 = buf_addr (de-pinnare)
    ; R3 = len
    caldeira_unpin_frame(vm, R2, R3)
    RET

Questo pattern è utile per operazioni dove non serve il risultato immediato: invio di pacchetti, logging su SD, aggiornamento display.

8.6 Gestione errori: due filosofie

Una syscall può fallire. Come comunica il fallimento alla VM?

8.6.1 Errore via R1 (recuperabile)

Il bytecode controlla il valore di ritorno:

static void sys_open_port(VMContext* vm) {
    uint32_t port = CALDEIRA_ARG_1(vm);
    int fd = hal_serial_open(port);
    if (fd <; 0) {
        CALDEIRA_RETURN(vm, 0xFFFFFFFF);  // errore: non posso aprire
        return;
    }
    CALDEIRA_RETURN(vm, fd);
}
MOV.S R1, 2
SYSCALL 0x93           ; sys_open_port(2)
CMP.S R1, 0xFFFFFFFF
BEQ @port_error        ; gestisci errore
; R1 = file descriptor valido

Vantaggio: la VM continua, il bytecode gestisce l'errore come preferisce.

8.6.2 Errore via fault (irrecoverable)

La syscall termina l'evento con un fault:

static void sys_open(VMContext* vm) {
    uint32_t* p = CALDEIRA_ARG_PTR(vm);
    if (!p) {
        caldeira_set_fault(vm, CALDEIRA_FAULT_NULL_POINTER);
        return;
    }
    *p = 42;
    CALDEIRA_RETURN(vm, 0);
}

Vantaggio: l'errore non passa inosservato. Se c'è un GUARD attivo, viene catturato. Se non c'è, l'evento termina con stato FAULT.

8.6.3 Differenza

La VM continua ✅ Il bytecode decide ❌ VM entra in FAULT
L'evento termina ✅ Normalmente ✅ Con pulizia scratch
Recuperabile if (R1 == -1) GUARD / UNGUARD
Visibilità Solo chi chiama Tutto il sistema
Quando usarlo Errori "normali" (file non trovato, timeout) Errori "strutturali" (puntatore nullo, stato invalido)

8.6.4 Codici fault: standard e custom

caldeira_set_fault(vm, code) accetta qualsiasi codice a 32 bit — non c'è validazione. Due famiglie:

  • Standard — le costanti CALDEIRA_FAULT_* (generate da VMFaultCode in

core/src/vm.h: CALDEIRA_FAULT_NULL_POINTER, CALDEIRA_FAULT_DIV_ZERO, ...). Sono i fault che la VM alza da sola: usarli da una syscall significa "simula questo errore di sistema" (raro, utile per i test).

  • Custom — qualunque valore inventato dal programmatore, es. 0x42 =

"il mio errore #66".

Lo spazio dei codici è diviso in due mondi (vedi l'enum in vm.h):

Range Uso
0x00 - 0x7F Errori utente: il tuo spazio. 0x00 = FAULT_USER_GENERIC (generico), 0x01-0x7F liberi per i codici custom
0x80 - 0xFFFFFF Errori di sistema: riservati alla VM (0x80 null pointer, 0x87 divisione per zero, ...). Evita di usarli per codici custom: si confonderebbero con i fault reali

Regole pratiche per i custom:

  • Definisci le costanti nel tuo header C (es. #define MY_FAULT_TIMEOUT 0x10)

o nel file syscalls.c del progetto.

  • Resta nel range 0x01-0x7F e entro 24 bit (0xFFFFFF), coerente con il

formato dei fault.

  • Il codice è leggibile lato C con caldeira_get_fault_code(vm) e compare nel

dump di sys_print_status; caldeira diagnose lo riporta con il valore esadecimale.

  • caldeira_set_fault si comporta esattamente come un fault della VM

(stessa strada di impl_FAULT): con un GUARD attivo il recovery cattura il fault (R14 = codice, salto all'handler); senza GUARD la VM va in FAULT (in debug: stop da fault con R14, riga colpevole a pc-4).

Dare un nome ai custom: .FAULTNAME (costante speciale)

Il debugger (registro sintetico STATUS, etichetta di R14, messaggi di stop) e caldeira diagnose mostrano per i custom il nome FAULT_UNKNOWN con l'esadecimale. Con la direttiva .FAULTNAME dichiari un nome leggibile per i TUOI codici nel sorgente del progetto (come .ABI per le syscall):

.FAULTNAME 0x10, MY_TIMEOUT
.FAULTNAME 0x11, MY_BAD_STATE

Name è un identificatore (mai stringhe) e si comporta come una costante speciale: la direttiva definisce anche la costante Name = code (stesso pool delle .CONST — un .CONST con lo stesso nome è un duplicato, E1304). Quindi FAULT MY_TIMEOUT, CMP.S R14, MY_TIMEOUT, ... assemblano senza doppia dichiarazione. Limiti: max 32 entry, nome max 32 caratteri; sintassi sbagliata → E1451, codice duplicato → E1453, limite → E1452.

  • Il debugger mostra FAULT 0x10 (MY_TIMEOUT) nel pannello Registri (STATUS e

R14) e nei messaggi di stop; caldeira diagnose riporta MY_TIMEOUT nel campo fault — entrambi leggono il sorgente, non il bytecode.

  • La VM a runtime non conosce i nomi custom: il banner di diagnostica

stampa Fault: 0x10 (FAULT_UNKNOWN) (come per eventi e syscall, il firmware ha solo numeri; i nomi standard FAULT_* restano, essendo parte del core).

  • Vale per i fault sollevati da FAULT imm nel bytecode E da

caldeira_set_fault nelle syscall C: il nome dichiarato è lo stesso.

Range di sistema: avviso W0002

L'istruzione FAULT imm accetta qualunque codice a 24 bit: il range 0x80-0xFF (fault standard della VM) non è bloccato, ma usarlo per un custom produce un warning non bloccante W0002 dell'assembler. Nessun warning se il codice è dichiarato con .FAULTNAME (uso legittimo del range alto) o è una costante che inizia per FAULT_ (codice standard esplicito). Un codice fuori contratto non è un PANIC: resta un fault normale (il GUARD lo recupera, R14 porta il valore esatto) — il PANIC è riservato alla corruzione della VM.

Direzione: entità custom del progetto (syscall e fault)

Oggi i nomi custom si dichiarano nel .clasto (.FAULTNAME) e i tool li leggono dal sorgente del progetto. La stessa filosofia vale per le syscall custom (syscalls.c): la dichiarazione dei nomi vive nel progetto, non nel bytecode. Evoluzione prevista: un file di definizione del progetto (stile events.def/syscalls.def, es. faults.def + syscalls.def locali) da cui si genera anche l'header C con le costanti — così .clasto e syscalls.c condividono gli stessi nomi senza doppio mantenimento, e l'ambiente di sviluppo (completions, debug, diagnosi) riconosce le entità battezzate dal progetto. La registrazione runtime in C (vm_syscall_register, caldeira_set_fault) resta il braccio esecutivo; il .def di progetto è la dichiarazione condivisa.

8.8 Accesso alla memoria dalla syscall

Una syscall riceve spesso indirizzi VM come argomenti (puntatori a buffer nello scratch o nel frame). Per tradurli in puntatori host usabili, l'SDK offre funzioni sicure:

// Lettura di 32 bit allineati
uint32_t* p32 = caldeira_get_u32ptr(vm, addr);
if (!p32) { CALDEIRA_RETURN(vm, 0xFFFFFFFF); return; }
uint32_t val = *p32;    // legge
*p32 = val + 1;          // scrive

// Lettura di 16 bit (controllo allineamento automatico)
uint16_t* p16 = caldeira_get_u16ptr(vm, addr);

// Lettura di 8 bit (nessun allineamento richiesto)
uint8_t* p8 = caldeira_get_u8ptr(vm, addr);

// Buffer generico (per DMA, memcpy)
void* buf = caldeira_get_buffer(vm, addr, len);

Queste funzioni:

  • Controllano i bounds — l'indirizzo deve essere in R_PRIVATE o R_SHARED
  • Controllano l'allineamento — u32ptr richiede allineamento a 4 byte
  • Restituiscono NULL se l'accesso non è valido (mai un crash)

8.9 Come progettare un'API di syscall

Una buona API di syscall è coerente, minimale, testabile. Ecco i principi.

8.9.1 Coerenza

Tutte le syscall seguono la stessa convenzione:

  • Input: R1 = primo argomento, R2 = secondo, R3 = terzo, R4 = quarto
  • Output: R1 = risultato (o 0xFFFFFFFF per errore)
  • Side effect: documentati esplicitamente
// Coerente: tutte le syscall GPIO seguono lo stesso schema
// 0x90: gpio_read(pin) ->; value
// 0x91: gpio_write(pin, value) ->; ok
// 0x92: gpio_set_mode(pin, mode) ->; ok
// 0x93: gpio_toggle(pin) ->; ok

8.9.2 Minimalità

Una syscall dovrebbe fare una cosa sola. Non una syscall "fai_tutto" che accende LED, legge sensori e invia email.

// Male
// sys_do_everything(mode, data) — cosa fa? Dipende da mode

// Bene
// sys_led_on(pin) — accende un LED
// sys_adc_read(pin) — legge un canale ADC
// sys_uart_send(data, len) — invia dati UART

8.9.3 Testabilità

Una syscall ben progettata è testabile in isolamento:

// Syscall pura: solo input → output, nessuno stato globale
static void sys_sum(VMContext* vm) {
    CALDEIRA_RETURN(vm, CALDEIRA_ARG_1(vm) + CALDEIRA_ARG_2(vm));
}
# Test su Linux (VM host)
lava test_sum.lava
# ->; R1 = 30 (se input sono 10 e 20)

8.9.4 Robustezza

Ogni syscall dovrebbe:

  1. Validare gli input — pin non validi? Buffer nulli? Lunghezze impossibili?
  2. Non fidarsi del bytecode — il bytecode potrebbe passare indirizzi sbagliati
  3. Restituire errore esplicito — mai crashare, sempre 0xFFFFFFFF o fault
static void sys_gpio_write(VMContext* vm) {
    uint32_t pin   = CALDEIRA_ARG_1(vm);
    uint32_t value = CALDEIRA_ARG_2(vm);

    if (pin >;= MAX_GPIO_PINS) {
        CALDEIRA_RETURN(vm, 0xFFFFFFFF);
        return;
    }
    if (value >; 1) {
        CALDEIRA_RETURN(vm, 0xFFFFFFFF);
        return;
    }

    hal_gpio_write(pin, value);
    CALDEIRA_RETURN(vm, 0);
}

8.10 Il caso d'uso: un sistema di logging completo

Mettiamo insieme i pattern in un esempio reale: un sistema di logging che accetta messaggi, li bufferizza, e li invia su UART.

Syscall di logging

// syscall 0xA0: sys_log(level, msg_addr) ->; ok
static void sys_log(VMContext* vm) {
    uint32_t level = CALDEIRA_ARG_1(vm);
    const char* msg = (const char*)caldeira_get_u8ptr(vm, CALDEIRA_ARG_2(vm));

    if (!msg) {
        CALDEIRA_RETURN(vm, 0xFFFFFFFF);
        return;
    }

    // Bufferizza nel frame (persistente, condiviso)
    uint32_t* log_buf = (uint32_t*)caldeira_get_buffer(vm, LOG_BUF_ADDR, LOG_BUF_SIZE);
    if (!log_buf) {
        CALDEIRA_RETURN(vm, 0xFFFFFFFF);
        return;
    }

    // Scrivi nel buffer circolare
    uint32_t pos = log_buf[0] % (LOG_BUF_SIZE / 64 - 1);
    log_buf[1 + pos] = level;
    // (copia il messaggio nel buffer...)
    log_buf[0]++;

    CALDEIRA_RETURN(vm, 0);
}

// syscall 0xA1: sys_flush_log() ->; ok
static void sys_flush_log(VMContext* vm) {
    switch (caldeira_get_resume_id(vm)) {
    case 0:
        // Avvia trasmissione UART del buffer log
        caldeira_pin_frame(vm, LOG_BUF_ADDR, LOG_BUF_SIZE);
        hal_uart_send_dma(LOG_BUF_ADDR, LOG_BUF_SIZE, &;flush_done);
        caldeira_yield(vm, 1);
        return;
    case 1:
        caldeira_unpin_frame(vm, LOG_BUF_ADDR, LOG_BUF_SIZE);
        CALDEIRA_RETURN(vm, 0);
    }
}

Registrazione

Uso dal bytecode

; Log di un messaggio
!LI R1, 1                    ; level = WARNING
!LI R2, msg_buffer           ; indirizzo del messaggio
SYSCALL 0xA0                 ; sys_log(WARNING, "temperatura alta")

; ... quando serve, svuota il buffer su UART
SYSCALL 0xA1                 ; sys_flush_log()
CMP R1, 0
BNE @log_error
; Log inviato con successo

8.11 Linee guida per progettare syscall

Fai

  • Una syscall, una responsabilità
  • Argomenti in R1–R4, risultato in R1
  • 0xFFFFFFFF = errore generico
  • Controlla ogni puntatore prima di usarlo
  • Yielda solo se l'attesa > 1ms (altrimenti il costo dello yield supera il beneficio)
  • Usa pin_frame per buffer asincroni
  • Documenta l'ABI: input, output, side effect

Non fare

  • Non usare variabili globali nelle syscall (se non strettamente necessario per l'HAL)
  • Non chiamare funzioni che bloccano (delay, polling) — yielda invece
  • Non scrivere oltre i limiti del buffer — la VM controlla, ma è malsano
  • Non assumere che i registri siano preservati tra chiamate — solo R8–R12 lo sono
  • Non superare il budget di slice — se la syscall è lunga, yielda o suddividi

👉 Ora tocca a te

  1. Fai l'inventario dell'HAL. Quante operazioni hardware fa il tuo sistema? GPIO, UART, I²C, SPI, ADC, timer? Ognuna è candidata a diventare una syscall.
  1. Progetta l'API delle syscall. Prendi 3 operazioni hardware e definisci l'ABI per ciascuna. Input in R1–R4. Output in R1. Errori in 0xFFFFFFFF. L'ABI è coerente?
  1. Implementa una syscall asincrona. Prendi un'operazione che richiede attesa (es. lettura sensore con conversione ADC). Implementala con caldeira_yield + callback.
  1. Testa la separazione. Scrivi una syscall, esegui la VM su Linux, verifica che funzioni. Poi porta la stessa syscall sul target embedded. Funziona senza modifiche? Se no, il layer HAL non è abbastanza astratto.
  1. Misura la latenza. Quanto tempo passa tra SYSCALL e la ripresa dopo uno yield? Nel caso peggiore? Questo è il costo del tuo "ponte" — se è troppo alto, forse l'operazione dovrebbe essere sincrona.

8.2 clasto: l'assemblatore

clasto è il compilatore che trasforma il codice assembly .clasto in bytecode .lava. È scritto in C, progettato per essere veloce, deterministico e portabile.

8.2.1 Uso base

# Compila un file sorgente
clasto programma.clasto -o programma.lava

# Compila con dimensione memoria personalizzata
clasto programma.clasto -o programma.lava --private-kb 8 --frame-kb 128

# Mostra informazioni sul bytecode generato
clasto programma.clasto -o programma.lava -v

# Output: 
#   Programma.clasto ->; programma.lava
#   Code size: 124 bytes (31 words)
#   Events: 3 handlers registered
#   Classes: 2 defined

8.2.2 Cosa fa clasto in 4 passi

Passo 1: Preprocessore (include + macro)
  • Espande .INCLUDE (con prevenzione inclusioni multiple)
  • Espande .MACRO con sostituzione parametri
  • Salva le definizioni .CONST per il passo 3

Passo 2: Prima passata (collect)
  • Raccoglie tutte le label (indirizzi simbolici)
  • Raccoglie le definizioni di classe (.CLASS)
  • Calcola la dimensione di ogni sezione

Passo 3: Seconda passata (encoding)
  • Traduce ogni istruzione in bytecode (32 bit per word)
  • Risolve i riferimenti a label (indirizzi assoluti)
  • Genera i Class Descriptor e la Class Table
  • Verifica la correttezza ABI (eventi, metodi, syscall)

Passo 4: Emit
  • Scrive il file .lava (header + bytecode + metadata)
  • Scrive il file .lst (listato assembly con indirizzi) se richiesto

8.2.3 Formato del file .lava

Il file .lava è un formato binario semplice: inizia direttamente con la tabella eventi, seguita dai metadata, poi dal codice. Non c'è un header con magic number — il bytecode è progettato per essere caricato direttamente in memoria senza parsing.

Offset    │ Contenuto
──────────┼────────────────────────────────────────
0x0000    │ Event table (64 × 4 byte, 256 byte totali)
0x0100    │ Metadata: class table pointer, class count,
          │           memory split, static offset & size
0x011C    │ Codice programma (istruzioni)

Il bytecode non viene mai modificato a runtime. La VM lo interpreta direttamente dalla memoria dove è stato caricato.

8.2.4 Listato assembly

clasto può generare un listato assembly con gli indirizzi di ogni istruzione:

clasto programma.clasto -o programma.lava -l programma.lst

Utile per debugging: sai esattamente quale bytecode corrisponde a quale istruzione.

8.3 lava: la VM player

lava è l'esecutore che carica un file .lava e avvia la VM. Su Linux funge da simulatore — lo stesso bytecode che girerà sull'ESP32 gira in un terminale Linux, identico.

8.3.1 Uso base

# Esegui un programma
lava programma.lava

# Esegui con stampa di debug
lava programma.lava -d

# Esegui con GDB stub (debug remoto)
lava programma.lava --gdb

# Esegui con 64 KB di frame e 8 KB di private
lava programma.lava --shared-kb 64 --private-kb 8

8.3.2 Modalità GDB

La VM incorpora un GDB stub che permette di debuggare il bytecode come se fosse C:

# Terminale 1: avvia la VM con GDB stub
lava programma.lava --gdb --gdb-port 1234

# Terminale 2: connetti GDB
gdb
(gdb) target remote :1234
(gdb) break *0x24        # breakpoint all'indirizzo 0x24
(gdb) continue
(gdb) info registers     # mostra R0-R15, PC, PSR
(gdb) step               # esegui un'istruzione
(gdb) x/10x 0x2000       # esamina memoria all'indirizzo 0x2000

Cosa puoi fare col GDB stub:

  • Breakpoint su indirizzi specifici
  • Single-step istruzione per istruzione
  • Ispezione di registri e memoria
  • Watchpoint su scritture/letture di memoria
  • Stack trace delle chiamate CALL

È un ambiente di debugging completo per bytecode, senza bisogno di hardware target.

8.3.3 Modalità verbose

lava programma.lava --verbose

Mostra ogni istruzione eseguita, con stato dei registri:

0x00000020: MOV.S R1, 10    → R1 = 10
0x00000024: MOV.S R2, 5     → R2 = 5
0x00000028: ADD R1, R2      → R1 = 15, PSR: Z=0 C=0
0x0000002C: HALT            → stato: EXITED

8.4 magma: container multi-VM

In configurazione multi-VM, più VM indipendenti condividono la stessa CPU e lo stesso frame arena. magma crea, ispeziona ed estrae container che le raggruppa tutte.

8.4.1 Due modi per creare un container

Modo 1: file .clasto con .VM / .END_VM

.VM alpha
.FILE ";alpha.clasto"
.VECTOR EVT_RESET(flags:FLG), main
main:
    MOV.S R1, 42
    HALT
.END_VM

.VM beta
.FILE ";beta.clasto"
.VECTOR EVT_RESET(flags:FLG), main
main:
    MOV.S R1, 99
    HALT
.END_VM

clasto rileva automaticamente 2+ blocchi e produce un .magma invece di un .lava.

Modo 2: compilazione separata + magma pack

# Compila ogni VM separatamente
clasto alpha.clasto -o alpha.lava
clasto beta.clasto -o beta.lava

# Crea il container
magma pack sistema.magma alpha.lava alpha beta.lava beta

8.4.2 Esecuzione multi-VM

lava sistema.magma

lava (su PC) e il firmware ESP32 caricano il container, creano le VM con frame condiviso, e le eseguono in round-robin: evento su VM1, poi VM2, poi VM1, ecc. Lo YIELD cooperativo garantisce che ogni VM abbia il suo tempo CPU. Il file .magma viene compilato su PC (dove clasto supporta .VM) e poi flashato sull'ESP32, che lo esegue senza modifiche.

┌─────────────────────────────────────────────┐
│                lava (host loop)              │
│                                              │
│  while(ci sono eventi da processare) {       │
│      for each VM:                            │
│          if evento in attesa → dispatch      │
│          if VM in pausa → riprendi           │
│  }                                           │
│                                              │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐ │
│  │   VM1    │   │   VM2    │   │   VM3    │ │
│  │scratch   │   │scratch   │   │scratch   │ │
│  │stack     │   │stack     │   │stack     │ │
│  └──────────┘   └──────────┘   └──────────┘ │
│                                              │
│  ┌─────────────────────────────────────────┐ │
│  │         FRAME ARENA (condiviso)          │ │
│  │  VM1 oggetti │ VM2 oggetti │ buffer DMA │ │
│  └─────────────────────────────────────────┘ │
└─────────────────────────────────────────────┘

8.4.3 Comunicazione inter-VM

Le VM comunicano attraverso il frame arena condiviso:

; VM1: scrive un valore nel frame
MOV.S R1, 42
ST32 R1, SHARED_ADDR    ; scrive nell'area condivisa del frame
FIRE EVT_DATA_READY     ; notifica VM2

; VM2: legge il valore (nell'handler EVT_DATA_READY)
LD32 R1, SHARED_ADDR    ; legge dall'area condivisa

Non c'è memoria copiata. Non c'è serializzazione. Non c'è IPC. C'è solo un buffer condiviso e un evento per sincronizzarsi.

8.5 caldeira: il ponte SDK

La libreria caldeira (generata da caldeira.h + caldeira.c) è il bridge tra il core VM e il codice C del target. Contiene:

  1. Prototipi delle funzioni SDK (caldeira_get_reg, caldeira_get_buffer, caldeira_yield, ecc.)
  2. Macro di comodo (CALDEIRA_ARG_1, CALDEIRA_RETURN, CALDEIRA_ARG_PTR)
  3. Costanti (CALDEIRA_STATE_, CALDEIRA_FAULT_)
  4. Forward declaration di VMContext (tipo opaco)

Quando compili per un target specifico:

# Genera il bridge SDK per il target linux
# (questo avviene automaticamente durante cmake)
python3 scripts/gen_caldeira_c.py \
    core/src/sdk.h \
    build/generated/caldeira/caldeira_linux.c

Il file generato include:

  • Le implementazioni delle funzioni caldeira_* (che nel core sono static inline, qui diventano simboli esportati)
  • I prototipi per l'utente (in caldeira.h)

8.6 La pipeline di sviluppo completa

Ecco come si sviluppa un progetto Caldeira dall'inizio alla fine:

Fase 1: Sviluppo su PC

# 1. Scrivi il programma in .clasto
code main.clasto

# 2. Scrivi le syscall in C
code syscall_gpio.c

# 3. Compila il bytecode
clasto main.clasto -o main.lava

# 4. Compila la VM + syscall per Linux
cmake --build build/Release
# → produce lava (VM player) + syscall condivise

# 5. Esegui e testa
lava main.lava -d

Fase 2: Debug

# 1. Avvia con GDB stub
lava main.lava --gdb --gdb-port 1234 &;

# 2. Connetti GDB
gdb -ex ";target remote :1234" \
    -ex ";break *0x30" \
    -ex ";continue"

# 3. Step, ispeziona registri, esamina memoria

Fase 3: Test automatici

# Script di test: esegue 100 scenari, verifica output
for i in $(seq 1 100); do
    lava test_$i.lava >; /tmp/out_$i.txt
    diff /tmp/out_$i.txt expected_$i.txt || echo ";Test $i fallito"
done

Fase 4: Deploy su target

# 1. Compila il bytecode (identico al PC — stesso file!)
clasto main.clasto -o main.lava

# 2. Compila la VM + syscall per ESP32
cmake --build build/Release --target caldeira-esp32

# 3. Carica il bytecode e la VM sull'ESP32
python3 deploy.py main.lava /dev/ttyUSB0

Il punto chiave: il file main.lava è identico su PC e su ESP32. Non devi ricompilare il bytecode per target diverso. Solo il bridge SDK (syscall) è target-specifico.

    -ex ";break *0x80" \         # break nel bytecode di VM1
    -ex ";info registers" \      # registri di VM1
    -ex ";continue"

La GDB stub ti permette di:

  • Fermare una VM mentre le altre continuano
  • Ispezionare il frame condiviso per vedere cosa ha scritto un'altra VM

9. Il futuro

"Il parallelismo non è fretta. È organizzazione. E l'organizzazione si costruisce con contratti, non con lock."

10.1 Il problema del multi-core embedded

I microcontrollori moderni hanno più core. ESP32 ha 2 core. Alcuni chip ne hanno 4 o 6. Ma il firmware embedded tradizionale fa fatica a sfruttarli.

Perché? Perché la memoria è condivisa. Due core che accedono alla stessa variabile senza sincronizzazione generano race condition. La soluzione classica (spinlock, mutex, sezioni critiche) è complessa, soggetta a errori, e distrugge le performance se usata male.

Caldeira VM ha un vantaggio strutturale: la memoria è già organizzata in regioni. Lo scratch è privato per VM. Il frame è condiviso. Questa separazione naturale si presta a un modello multi-core senza race condition.

10.2 Il modello: una VM per core

La configurazione multi-core più semplice: una VM dedicata per core.

┌─────────────────────────────────────────────────┐
│                   Chip (2 core)                  │
│                                                  │
│  Core 0                     Core 1              │
│  ┌─────────────────┐       ┌─────────────────┐  │
│  │   VM1           │       │   VM2           │  │
│  │   • Controllo   │       │   • Interfaccia │  │
│  │   • Sensori     │       │   • Display     │  │
│  │   • Attuatori   │       │   • Logging     │  │
│  │                 │       │                 │  │
│  │  Esecuzione VM  │       │  Esecuzione VM  │
│  └────────┬────────┘       └────────┬────────┘  │
│           │                        │           │
└───────────┼────────────────────────┼───────────┘
            │                        │
            ▼                        ▼
     ┌─────────────────────────────────────┐
     │       FRAME ARENA (condiviso)        │
     │  VM1: buffer motore | VM2: buffer   │
     │  DMA UART          | display         │
     └─────────────────────────────────────┘

Ogni core esegue la propria istanza della VM su contesti diversi. Le VM condividono il frame ma hanno scratch e stack privati. La comunicazione avviene attraverso il frame + eventi.

10.2.1 Come si realizza

Non serve un sistema operativo. Serve solo un lock per la coda eventi (già implementato con hal_spinlock_t) e la consapevolezza che due core possono chiamare vm_kernel_post contemporaneamente.

Lo spinlock nella coda eventi garantisce che vm_kernel_post sia sicura da entrambi i core. Il frame condiviso è accessibile direttamente (le VM scrivono in regioni diverse o si coordinano via eventi).

10.3 Frame condiviso: nessuna copia tra core

Il frame è in memoria RAM accessibile da entrambi i core. VM1 (core 0) può scrivere un buffer di lettura sensori, VM2 (core 1) può leggerlo senza copia:

; VM1 (core 0): scrive dati sensore nel frame
.VECTOR TICK_10MS(flags:FLG), read_sensor

read_sensor:
    MOV.S R1, SENSOR_PIN
    SYSCALL SYS_ADC_READ
    ST32 R1, SENSOR_DATA_ADDR    ; scrive nel frame (accessibile da VM2)
    FIRE EVT_SENSOR_READY        ; notifica VM2
    RET

; VM2 (core 1): legge dati sensore dal frame
.VECTOR EVT_SENSOR_READY(flags:FLG), process_sensor

process_sensor:
    LD32 R1, SENSOR_DATA_ADDR    ; legge dal frame (nessuna copia!)
    ; elabora...
    RET

Il frame è memoria condivisa senza lock espliciti. La sincronizzazione è implicita: VM1 scrive prima di mandare l'evento, VM2 legge dopo aver ricevuto l'evento. La coda eventi fa da barriera di memoria (grazie allo spinlock).

10.4 Sfide e limiti

10.4.1 Concorrenza sul frame

Due core potrebbero scrivere sulla stessa area del frame contemporaneamente. La soluzione: partizionamento statico. Ogni VM ha una regione dedicata del frame, definita a compile-time.

// Ogni VM scrive solo nella sua area
#define FRAME_AREA_VM1  0x0000  // 0-1023: area VM1
#define FRAME_AREA_VM2  0x0400  // 1024-2047: area VM2
#define FRAME_AREA_SHRD 0x0800  // 2048-4095: area condivisa (con evento)

L'area condivisa è quella usata per la comunicazione inter-VM, dove il protocollo è: scrivi prima, notifica dopo.

10.4.2 Determinismo su multi-core

La VM è determinista su un singolo core. Su più core, l'ordine di esecuzione degli eventi non è deterministico — dipende dallo scheduling hardware dei core.

Se il determinismo è critico, la soluzione è: esegui tutto su un core, usa l'altro per attività non critiche (logging, display, comunicazione). Il core principale resta deterministico.

10.5 Scenario reale: sistema di acquisizione a 2 core

Core VM Compiti Budget
0 Controllo Lettura sensori (10ms), controllo motore (1ms), logica sicurezza 5000 istruzioni
1 Comunicazione UART, WiFi, logging SD, interfaccia utente 5000 istruzioni

Core 0 è deterministico, mission-critical. Core 1 è best-effort, ma isolato — se crasha, non impatta core 0.

Stesso kernel. Stesso frame. Zero mutex nel codice applicativo. La VM garantisce l'isolamento.

11.2 Cosa Caldeira abilita che prima non era possibile

11.2.1 Un linguaggio di controllo per un dominio specifico

Prima di Caldeira, per creare un linguaggio per PLC su un ESP32 dovevi scrivere un interprete completo — con parser, runtime, garbage collector. Un progetto di 6-12 mesi.

Con Caldeira, scrivi un compilatore dal tuo DSL a .clasto in poche settimane. La VM fa tutto il resto: esecuzione, memoria, debug, fault recovery.

11.2.2 Firmware deterministico con isolamento totale

Prima di Caldeira, l'unico modo per avere isolamento tra task era mettere un RTOS con MMU (es. Linux su MCU). Che richiede un chip potente, molta RAM, e complessità enorme.

Con Caldeira, hai isolamento su un ESP32 con 512 KB di RAM. La VM controlla ogni accesso alla memoria. Un evento non può corrompere un altro evento.

11.2.3 Stesso bytecode su MCU, PC e cloud

Prima di Caldeira, il firmware era legato all'hardware. Per testarlo su PC serviva un simulatore ad-hoc. Per portarlo su un altro MCU servivano settimane di lavoro.

Con Caldeira, il .lava è lo stesso ovunque. Lo sviluppi su Linux, lo testi in CI, lo deployi su ESP32. Zero modifiche. È la promessa "write once, run anywhere" mantenuta per l'embedded.

11.2.4 Debug remoto di bytecone su un satellite

Con GDB stub integrato, puoi connetterti a una VM in esecuzione su un dispositivo remoto e fare debugging come se fosse locale. Breakpoint, single-step, ispezione memoria. Su un satellite in orbita o su un sensore in Antartide.

11.2.5 Multi-VM su singolo core (o multi-core)

Più VM isolate sullo stesso chip, o su core diversi. Con comunicazione via frame condiviso. Senza OS, senza MMU, senza lock espliciti.

11.3 Cosa Caldeira NON è

Onestà intellettuale, di nuovo.

Caldeira non è per:

  • Loop di controllo a > 10 kHz (servo motori, alimentatori switching)
  • Elaborazione numerica pesante (FFT, AI inference)
  • Sistemi dove ogni microsecondo conta
  • Sistemi con vincoli di memoria estremi (< 32 KB RAM)

Caldeira è per:

  • Sistemi con logica complessa (multi-sensore, multi-attuatore, protocolli)
  • Prodotti che devono durare anni senza manutenzione
  • Dispositivi programmabili da non-esperti (via DSL)
  • Progetti dove il costo del debug supera il costo della VM

11.4 Il futuro

Caldeira VM è un progetto giovane. Ha già le fondamenta: una VM determinista, un assemblatore, un player, un SDK, un sistema di classi, un modello di memoria regionale.

Il futuro dipende da chi la userà. Da chi costruirà:

  • Il primo DSL industriale per il controllo di processo
  • Il primo compilatore da Python a bytecode Caldeira
  • Il primo visual editor per logica di automazione
  • Il primo corso universitario su "VM per sistemi embedded"
  • La prima certificazione safety su Caldeira

Caldeira non compete con FreeRTOS, con Zephyr, con MicroPython. Li abilita a fare cose che da soli non potrebbero fare.

11.5 La visione

Tra 5 anni, vorrei vedere:

Un ingegnere dell'automazione che scrive:

Questo è il futuro che Caldeira abilita. Non "un'altra VM per l'embedded". Ma l'infrastruttura per costruire i linguaggi dell'embedded di domani.
